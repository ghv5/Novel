# 服务治理-服务发现与负载均衡演进

## 1. 场景与边界

- 何时会遇到：单体拆成多个服务后，订单服务需要调用用户服务和商品服务；调用方开始面对“对方地址会变、会有多实例、会上下线”的问题。
- 业务目标：让订单服务在**不知道下游具体 IP** 的前提下，稳定地找到可用实例并发起 HTTP 调用；在多实例部署时能把请求分摊出去；实例上下线能被感知。
- 非目标：不涉及 RPC 序列化协议设计、异步调用、服务网格（Sidecar）方案；也不涉及注册中心自身的高可用部署与多机房。
- 适用前提与规模假设：Spring Cloud Hoxton.SR12 + Nacos 服务发现；调用方与服务提供方都是 Spring Boot 应用；下游实例数量为个位数到几十个，属于教学/中小规模场景。

## 2. 约束与难点

- **地址漂移**：容器化或弹性扩缩容后实例 IP、端口不固定，硬编码不可持续；重启一次就可能换地址。
- **多实例选择**：注册中心只给出实例清单，选择哪个实例由调用方决定；选择逻辑要能被替换和观测。
- **调用可靠性**：地址拿到了不代表服务可用，需要超时、重试、容错（见“服务调用”与“服务容错”）。
- **元数据一致性**：注册中心实例列表有延迟，刚下线的实例可能仍被调用到；Nacos 临时实例与持久实例的剔除行为不同。
- **服务名契约**：服务名是字符串，编译期不校验，写错只在运行期暴露。
- **可观测性**：负载均衡结果、目标实例需要能被日志/链路追踪记录，否则排障只能靠猜。
- **模块依赖副作用**：`shop-utils` 的 `pom.xml` 引入了 `spring-boot-starter-web`、`mybatis-plus-boot-starter`、`mysql`、`druid`，因为 `shop-bean` 依赖 `shop-utils`，所以**所有业务模块都间接拿到 Web 与数据库依赖**。这让 `shop-utils` 事实上成了“公共基础模块”，配置 `@EnableDiscoveryClient`、Mapper 扫描时容易产生隐性耦合。

## 3. 项目中的实现链路

项目用同一个 `submit_order` 业务，逐步演进出四版调用方式，这是最直观的“服务治理能力如何被引入”的证据链。

```text
V1 硬编码地址        OrderServiceV1Impl  ->  http://localhost:8060 / http://localhost:8070
V2 手动查注册中心    OrderServiceV2Impl  ->  DiscoveryClient.getInstances(name).get(0)
V3 手动随机负载均衡  OrderServiceV3Impl  ->  DiscoveryClient.getInstances(name) + Random
V4 声明式负载均衡    OrderServiceV4Impl  ->  RestTemplate + @LoadBalanced("http://server-user")
V5+ Feign 声明式     ProductService/UserService(@FeignClient) 见“服务调用”篇
```

服务注册侧：`shop-user`、`shop-product`、`shop-order`、`shop-gateway` 的启动类都标注 `@EnableDiscoveryClient`，并在 `bootstrap.yml` 配置 `spring.cloud.nacos.discovery.server-addr`，进程启动后自动注册到 Nacos。

```text
应用启动
  -> 读 bootstrap.yml: spring.application.name / nacos.discovery.server-addr
  -> 向 Nacos 注册实例(IP:端口, 服务名)
  -> 定时心跳
调用方
  -> 通过服务名查实例列表(DiscoveryClient / LoadBalancer)
  -> 选择实例 -> 发起 HTTP
```

## 4. 关键选型与权衡

- 【代码事实】项目最终选择 **Nacos 注册中心 + 客户端负载均衡 + `@LoadBalanced RestTemplate`**，随后进一步演进到 Feign。
- 【工程推断】V1→V4 的演进是在演示“能力分层引入”，而不是一步到位。依据是四个类同名同逻辑、只改了调用方式，且专栏章节与版本号一一对应。置信度高。
- **解决了什么**：调用方不再需要知道实例地址；多实例可分摊流量；注册中心上下线可被感知。
- **牺牲了什么 / 风险**：
  - 多了一层“服务名 → 实例”解析，新增“服务找不到/实例列表为空”的故障面；
  - `@LoadBalanced` 的默认策略与重试行为是隐式的，不看源码/配置很难判断；
  - V2/V3 的 `getInstances(name).get(0)` 与“自研随机”没有任何容错，实例为空直接 `IndexOutOfBoundsException`；
  - `@LoadBalanced RestTemplate` 需要手动设置超时，默认无读取超时会长时间阻塞。
- 【项目中未发现明确依据】没有发现 Ribbon/LoadBalancer 具体策略（轮询/随机/权重/同机房）的显式配置；`application-sentinel.yml` 中只有被注释掉的 Ribbon `NFLoadBalancerRuleClassName` 示例（第 4-6 行），未启用。也没有 `Spring Cloud LoadBalancer` 与 Ribbon 的取舍说明（Hoxton.SR12 默认仍为 Ribbon）。

## 5. 关键工程实现

### 5.1 四版写法对照

| 版本 | 地址来源 | 实例选择 | 容错 | 代码定位 |
|---|---|---|---|---|
| V1 | 字符串常量 | 无（单实例） | 无 | `OrderServiceV1Impl.java:46` |
| V2 | `DiscoveryClient` | `get(0)` | 无 | `OrderServiceV2Impl.java:93` |
| V3 | `DiscoveryClient` | `Random` | 无 | `OrderServiceV3Impl.java:95-98` |
| V4 | 服务名 | `@LoadBalanced` 默认策略 | 无 | `OrderServiceV4Impl.java:52` |

### 5.2 手动发现与手动负载均衡

```java
// V2：只取第一个实例，顺序由注册中心返回，不是负载均衡
ServiceInstance instance = discoveryClient.getInstances(serviceName).get(0);

// V3：在实例列表中随机挑一个，属于最小可用的负载均衡
List<ServiceInstance> instances = discoveryClient.getInstances(serviceName);
int index = new Random().nextInt(instances.size());
ServiceInstance serviceInstance = instances.get(index);
String url = serviceInstance.getHost() + ":" + serviceInstance.getPort();
```

共同缺陷：
- 没有空列表保护（`get(0)`/`nextInt(0)` 会抛异常）；
- 没有健康检查与重试；
- 每次调用都查一次实例列表，没有本地缓存（V2/V3 未使用框架缓存）。

### 5.3 `@LoadBalanced` 改变了什么

```java
@Bean
@LoadBalanced
public RestTemplate restTemplate() { return new RestTemplate(); }
```

`@LoadBalanced` 会为 `RestTemplate` 注入一个 `ClientHttpRequestInterceptor`（Ribbon/LoadBalancer 实现）。此后：

```java
restTemplate.getForObject("http://server-user/user/get/1001", User.class);
//                             ^^^^^^^^^^^ 逻辑服务名，被拦截器替换为真实 host:port
```

这是 V1（硬编码 IP）与 V4（服务名）写法只差一个字符串、行为却完全不同的原因。

### 5.4 服务名与配置的对应关系

| 应用 | `spring.application.name` | Nacos group | 端口（Nacos 配置导出） |
|---|---|---|---|
| 用户 | `server-user` | `user_group` | 8060，context-path `/user` |
| 商品 | `server-product` | `product_group` | 8070，context-path `/product` |
| 订单 | `server-order` | `order_group` | 8080，context-path `/order` |
| 网关 | `server-gateway` | `gateway_group` | 10002（网关本地 10001） |

注意：Feign 接口里写的 `/product/get/{pid}` 是**包含 context-path 的完整路径**（`ProductController` 本身没有 `@RequestMapping` 前缀）。因此修改 context-path 会同时影响 Feign 契约，属于隐性耦合。

## 6. 踩坑、根因与排障

| 性质 | 现象 | 根因 | 项目处理 | 仍存缺口 | 验证或排查方法 |
|---|---|---|---|---|---|
| 潜在风险 | 实例为空时 `IndexOutOfBoundsException` | V2/V3 无空列表判断 | 未处理 | 需降级返回业务错误 | 停掉下游服务后调用 `submit_order`，看异常类型 |
| 潜在风险 | 请求路由到已下线实例 | 心跳延迟 + 调用方缓存 | 未处理 | 需超时/重试/熔断 | 滚动重启下游并压测 |
| 潜在风险 | 负载策略不符合预期 | 未显式配置策略 | Ribbon 配置被注释 | 无法从配置看出策略 | 多实例部署，日志打印目标 host 统计分布 |
| 潜在风险 | 服务名写错运行期才报错 | 字符串无编译校验 | 未处理 | 契约测试/启动自检 | 改错 `server-user` 观察报错时机 |
| 潜在风险 | `RestTemplate` 无超时线程堆积 | 未配置超时 | 未处理 | 显式设 connect/read timeout | 注入延迟观察线程数 |
| 潜在风险 | 改 context-path 导致 Feign 404 | Feign 路径含 context-path | 未处理 | 契约化路径 | 修改后回归所有 Feign 接口 |
| 潜在风险 | 公共模块携带 Web/DB 依赖导致扫描意外 | `shop-utils` 依赖 web/mybatis | 未处理 | 分离 `shop-common` 与 `shop-db` | 查看各服务启动扫描的 Bean |

## 7. 可迁移的落地方案

【落地建议】

1. **统一在 `bootstrap.yml` 配置注册中心**，给每个服务固定的 `spring.application.name`；服务名与业务域绑定，不用端口/环境名。
2. **调用下游统一用“服务名 + 声明式客户端”**，禁止出现 `localhost`/固定 IP。可保留一版 `DiscoveryClient` 手动调用作为排障工具。
3. **显式设置超时与重试**：`RestTemplate` 的连接/读取超时、Feign 的 `connectTimeout`/`readTimeout`；只对幂等 GET 重试并限制次数。
4. **显式配置负载策略**（轮询/随机/权重/同机房），并在日志或链路中记录选中的实例。
5. **为空实例列表和全不健康设计降级**，返回明确业务错误并告警。
6. **服务名与 context-path 纳入契约管理**：把 Feign 路径、context-path、服务名当作接口契约的一部分，有变更检查。
7. **分离公共模块职责**：不要让“工具模块”携带 Web/DB 依赖，避免所有服务被动继承。
8. **上线前滚动发布压测**，确认实例下线能自动切走。

### 演进顺序

`硬编码 → 注册中心手动查询 → 手动负载均衡 → 声明式负载均衡 → 超时/重试/熔断 → 灰度与同机房路由`。每一步都应在你能解释“上一层为什么痛”之后再引入。

## 8. 替代方案与适用边界

- **`@LoadBalanced RestTemplate`**：调用方少、接口简单、团队熟悉 Spring Cloud 原生栈。
- **OpenFeign**：接口多、需要声明式契约与统一降级（见下一篇）。
- **服务网格 / DNS 服务发现**：实例规模大、多语言、需要统一流量治理时，把发现与负载均衡下沉到网格。
- **K8s Service + DNS**：已在 Kubernetes 且不需要 Spring Cloud 特有灰度时，很多注册中心能力可被替代。
- **注册中心选型**：Nacos（本项目，注册+配置一体）、Eureka（已停更）、Consul、ZooKeeper（CP）。按一致性要求与运维成本选择。

判断依据：服务/实例数量、是否跨语言、是否需要客户端精细化路由、团队对注册中心运维的掌控力。

## 9. 验收清单

- [ ] 所有跨服务调用都不含硬编码 IP/端口（全局搜索 `localhost:`、`127.0.0.1:` 于业务代码）。
- [ ] 服务名/context-path 变更会同步更新调用方，并有自动化检查（契约测试/启动自检）。
- [ ] 实例列表为空、实例全部不可用时，返回明确业务错误并有告警。
- [ ] 连接超时、读取超时、重试次数显式配置且经过压测验证。
- [ ] 负载策略显式配置，并通过日志验证分布均匀。
- [ ] 滚动发布期间无因实例上下线导致的持续错误。
- [ ] 注册中心不可用时，服务行为符合预期（快速失败或用本地缓存清单）。
- [ ] 公共模块不携带业务无关的 Web/DB 依赖。
