# 服务网关-路由过滤与灰度发布

## 1. 场景与边界

- 何时会遇到：多个微服务需要统一入口，做鉴权、限流、跨域、协议适配、灰度路由；客户端不希望直连每个服务。
- 业务目标：把外部请求按路径路由到内部服务；在网关上做**跨域、访问日志、限流**等横切处理；为灰度发布预留扩展点。
- 非目标：不展开网关高可用部署、不涉及 WebSocket/长连接、不深入响应式背压调优。
- 适用前提与规模假设：Spring Cloud Gateway（WebFlux）；后端服务已注册到 Nacos；路由目标以服务名 `lb://` 为主。

## 2. 约束与难点

- **路由来源**：手写路由（`application.yml`/Nacos）与基于注册中心的动态路由（discovery locator）会同时存在，可能重复或冲突。
- **Profile 与配置来源**：仓库有多份 `application-*.yml`，但 `bootstrap.yml` 只激活 `dev` 且配置来自 Nacos，本地 profile 文件未必生效——这是本项目最容易误解的点。
- **过滤器执行顺序**：全局过滤器、路由级过滤器、Sentinel 过滤器、断言顺序都会影响结果；顺序错了会出现“限流没生效”或“日志拿不到耗时”。
- **线程模型**：Gateway 是 Reactive 的，不能用 Servlet 的 `ThreadLocal` 思路；跨阶段传值要用 `exchange.getAttributes()`。
- **配置缺失**：某些 Bean 强依赖配置键，缺失即启动失败。
- **灰度语义**：灰度需要路由到不同版本实例，依赖元数据/标签，不是打印一行日志。
- **可观测性**：入口过滤器容易打印“看起来对、其实错”的信息（见下）。

## 3. 项目中的实现链路

```text
客户端 -> server-gateway(10001 本地 / 10002 Nacos)
  -> 全局过滤器: GatewayFilterConfig(@Order -1) / GlobalGatewayLogFilter
  -> 路由匹配: Path 断言 (+ 自定义 Name 断言)
       uri: lb://server-user / http://localhost:8060
  -> 路由级过滤器: StripPrefix=1 / Grayscale=true(自定义)
  -> Sentinel 网关过滤器 + 自定义 API 与限流
  -> 转发到目标服务
  -> 后置处理: 记录耗时等
```

### 3.1 多份配置与 profile 策略（关键）

| 配置文件 | 路由方式 | 是否默认生效 | 说明 |

## 4. 关键选型与权衡

- 【代码事实】路由方式同时保留 **手工 `routes`** 与 **discovery locator 自动路由**；`application-nacos.yml` 两者都开启。
- 【代码事实】限流规则既可用代码加载（`initGatewayRules`），也可由 Dashboard 配置；项目把代码加载注释掉，实际走 Dashboard。
- **解决了什么**：统一入口；按路径路由；跨域集中配置；全局/局部过滤器可插拔；为限流和灰度留扩展点。
- **牺牲了什么 / 风险**：
  1. **配置来源不唯一**：本地 6 份 yml（大多带 `localhost`）+ Nacos 一份，谁生效取决于 profile，容易改错地方。`application.yml` 全注释更像“文档”而非配置。
  2. **`route-id-prefix` 强依赖**：`GatewayConfig` 用 `@Value` 无默认值注入（第 59-60 行），在只加载无该键的 profile（如 `application-simple`）时 `@PostConstruct` 前的字段注入会失败，导致上下文启动失败。
  3. **手工路由与 locator 重复**：`application-nacos.yml` 中手工路由 id `user-gateway`，locator 路由 id 带 `gateway-` 前缀；两者 Path 断言不同（`/server-user/**` 与 locator 生成的规则），一般不同时命中，但维护两份映射增加心智负担，且 `order` 全为 1 无区分度。
  4. **`GlobalGatewayLogFilter` 打印的 host/port 语义错误**：`exchange.getRequest().getURI()` 在 Gateway 中代表**进入网关的原始请求**，其 host 是网关对外的主机（或 Host 头），不是被选中的后端实例。因此日志里的“访问接口主机/端口”具有误导性，排障时无法据此定位后端。正确做法是从路由后的 `GATEWAY_REQUEST_URL_ATTR` 或 `ServerWebExchangeUtils` 中取目标 URL。
  5. **灰度只打印日志**：`GrayscaleGatewayFilterFactory` 未做任何路由决策，属演示级。
  6. **限流响应不一致**：网关返回 HTTP 200 + code 1001，Web 侧返回 HTTP 500（见“服务容错”“接口契约”篇）。
  7. **`allow-bean-definition-overriding: true`**：为解决 Bean 冲突而开启，但会掩盖真正的 Bean 覆盖问题，需谨慎。
- 【项目中未发现明确依据】没有鉴权过滤器、没有 JWT/OAuth 接入；灰度所需的实例元数据（version 标签）也没有配置。

## 5. 关键工程实现

### 5.1 自定义路由级过滤器

```java
@Component
public class GrayscaleGatewayFilterFactory
        extends AbstractGatewayFilterFactory<GrayscaleGatewayFilterConfig> {
    public GrayscaleGatewayFilterFactory() { super(GrayscaleGatewayFilterConfig.class); }

    @Override
    public GatewayFilter apply(GrayscaleGatewayFilterConfig config) {
        return (exchange, chain) -> {
            if (config.isGrayscale()) { System.out.println("开启了灰度发布功能..."); }
            return chain.filter(exchange);
        };
    }

    @Override
    public List<String> shortcutFieldOrder() { return Arrays.asList("grayscale"); }
}
```

配置写法 `- Grayscale=true`：Spring Cloud Gateway 把 `Grayscale` 映射到 `GrayscaleGatewayFilterFactory`，`true` 按 `shortcutFieldOrder` 绑定到 `grayscale` 字段。命名约定：类名 `<Name>GatewayFilterFactory`，配置里用 `<Name>`。

### 5.2 全局过滤器与耗时统计（Reactive 正确姿势）

```java
// 前置：把开始时间放进 exchange 属性（不能用 ThreadLocal）
exchange.getAttributes().put(BEGIN_VISIT_TIME, System.currentTimeMillis());
return chain.filter(exchange).then(Mono.fromRunnable(() -> {
    Long begin = exchange.getAttribute(BEGIN_VISIT_TIME);
    // 后置：计算耗时
}));
```

错误示范（本项目日志字段）：

```java
// 这是“进入网关的请求 URL 的 host”，不是后端实例
exchange.getRequest().getURI().getHost();
// 正确应取路由目标，例如:
// URI target = exchange.getAttribute(ServerWebExchangeUtils.GATEWAY_REQUEST_URL_ATTR);
```

### 5.3 自定义断言

```java
public Predicate<ServerWebExchange> apply(NameRoutePredicateConfig config) {
    return exchange -> {
        String name = exchange.getRequest().getQueryParams().getFirst("name");
        if (StringUtils.isEmpty(name)) name = "";
        return name.equals(config.getName());
    };
}
```

命名约定：类名以 `RoutePredicateFactory` 结尾，配置里去掉后缀用 `Name=binghe`。该断言被注释，未启用。

### 5.4 网关限流的两个关键点

```java
// 1) 用 route-id-prefix + 服务名拼出与 locator 一致的资源名
rules.add(getGatewayFlowRule(getResource("server-user")));   // 资源名 gateway-server-user

// 2) 自定义限流响应
GatewayCallbackManager.setBlockHandler((exchange, throwable) -> {
    map.put("code", 1001);
    map.put("codeMsg", "接口被限流了");
    return ServerResponse.status(HttpStatus.OK).contentType(APPLICATION_JSON_UTF8)...;
});
```

`GatewayConfig` 注释里解释得很清楚：Sentinel 为 locator 生成的 API 名称是 `route-id-prefix + 目标服务名`，为了让请求链路中的资源名与流控规则一致，规则 resource 必须按同样规则拼接。项目 `initCustomizedApis()` 定义了 `user_api1`（前缀 `/server-user/user/api1/**`）与 `user_api2`（精确 `/server-user/user/api2/demo1`），但 `initGatewayRules()` 已被注释，所以这些 API 分组在代码层面没有配套规则，需在 Dashboard 手动关联。

### 5.5 过滤器顺序一览

| 过滤器 | 类型 | 顺序 | 作用 |
|---|---|---|---|
| `SentinelGatewayFilter` | 全局 | `HIGHEST_PRECEDENCE` | 网关限流（最先） |
| `GatewayFilterConfig#globalFilter` | 全局 | `-1` | 前置/后置日志 |
| `GlobalGatewayLogFilter` | 全局 | `0` | 访问耗时统计 |
| `StripPrefix=1` | 路由级 | 默认 | 去掉路径前缀 |
| `Grayscale` | 路由级 | 默认 | 灰度（仅打印） |

## 6. 踩坑、根因与排障

| 性质 | 现象 | 根因 | 项目处理 | 仍存缺口 | 验证或排查方法 |
|---|---|---|---|---|---|
| 已证实（代码） | 日志中的“后端主机/端口”不是真实后端 | 打印的是入站请求 URI | 未处理 | 需取路由目标 URL | 多实例部署，对比日志 host 与实际实例 |
| 潜在风险 | 启动失败：无法解析 `route-id-prefix` | `@Value` 强依赖该键 | 仅在含 locator 的 profile 可启动 | 设默认值 `@Value("${...:}")` | 用 `application-simple` profile 启动 |
| 潜在风险 | 改本地 yml 不生效 | 实际读 Nacos 配置 | 未处理 | 明确配置来源 | 启动日志/`actuator/env` 确认 |
| 潜在风险 | 限流规则配了不生效 | 代码规则被注释，资源名需与 locator 前缀一致 | 依赖 Dashboard | 缺规则版本化 | Dashboard 查看资源名与规则 |
| 潜在风险 | 手工路由与 locator 重复 | 两者同时开启 | 未处理 | 二选一或统一命名 | `actuator/gateway/routes` 看路由表 |
| 潜在风险 | 灰度只打印不生效 | filter 无路由逻辑 | 演示实现 | 基于 header/权重的 `lb` 策略 | 灰度请求观察目标实例 |
| 潜在风险 | 跨域 `*` 与凭据冲突 | `allowedOrigins:"*"` + `allowCredentials:true` | 配置如此 | 浏览器会拒绝 | 浏览器控制台看 CORS 报错 |
| 潜在风险 | Bean 覆盖掩盖问题 | `allow-bean-definition-overriding: true` | 配置如此 | 谨慎使用 | 启动日志搜索覆盖告警 |

## 7. 可迁移的落地方案

【落地建议】

1. **路由来源二选一**：全部手工路由（可控、可审计）或全部 locator（省事但命名不可控）；混用时给路由设明确 `order` 并写测试。
2. **配置来源唯一化**：把网关配置集中到配置中心，本地只保留一份可运行的最小配置；删除或明确标注“仅教学用”的 profile 文件。
3. **网关只做横切**：鉴权、限流、日志、跨域、协议转换；不要在网关写业务判断。
4. **过滤器顺序显式化并用常量表示**，写顺序断言测试。
5. **配置键给默认值**：`@Value` 加默认值或改 `@ConfigurationProperties`。
6. **限流响应契约与服务端统一**：统一业务码与 HTTP 状态码。
7. **灰度基于元数据**：给实例打 `version` 标签，用权重/header 路由，保留回滚开关。
8. **可观测性**：网关记录 traceId、路由目标实例、状态码、耗时，并与服务端链路打通。
9. **谨慎使用 Bean 覆盖**：只在对第三方框架做可控扩展时打开，并配套测试。

### 最小闭环

`统一路由来源 + 统一配置来源 + 鉴权限流日志跨域四类过滤器 + 统一响应契约 + 顺序测试 + 灰度元数据 + 入口指标`。

## 8. 替代方案与适用边界

- **Spring Cloud Gateway**：Spring 生态、需要编程式过滤器时首选；注意 WebFlux 学习成本。
- **Nginx / OpenResty**：纯路由与静态资源、极致性能；业务级灰度/鉴权集成不如 SDK 灵活。
- **APISIX / Kong**：需要插件生态、多语言、独立网关团队。
- **Ingress / Service Mesh Gateway（Istio）**：已在 K8s 且需要统一 mTLS、流量治理时下沉。

判断依据：团队技术栈、是否需要业务级过滤、是否已上 K8s/网格、运维成本。
