# 接口契约-统一返回与全局异常处理

## 1. 场景与边界

- 何时会遇到：多个服务对外/对内提供 HTTP 接口，返回体格式不统一、异常直接吐堆栈、调用方无法区分“业务失败”和“系统故障”。在微服务里这个问题会被放大——一个服务的异常契约会成为所有调用方的负担。
- 业务目标：定义一套**跨服务一致的响应结构与错误语义**，让：
  1. 所有正常返回形状一致；
  2. 异常有统一出口、不泄露内部细节；
  3. 调用方（尤其是 Feign）能用同一段代码判定成功/失败/降级。
- 非目标：不涉及国际化错误码体系、不做 API 网关层的错误转换（见“服务网关”篇）、不展开 JSR-303 校验框架（项目未使用）。
- 适用前提与规模假设：Spring MVC；同步 HTTP 接口；调用方与服务方同属一个团队，可约定契约。

## 2. 约束与难点

- **HTTP 状态语义 vs 业务码**：业务失败应返回 HTTP 200 + 业务码，还是 HTTP 4xx/5xx？两种选择对 Feign、网关、监控、重试策略影响完全不同。
- **异常分类**：参数错误（4xx）、业务规则失败（4xx/200+码）、系统故障（5xx）、限流熔断（429/503）需要区分，否则调用方无法决定“是否重试”。
- **全局处理的覆盖范围**：`@RestControllerAdvice` 只能处理进入 Controller 后的异常，过滤器/拦截器阶段、序列化阶段的异常不在其内。
- **参数校验的落地位置**：在 DTO 的 `isEmpty()` 里手写校验，还是用 Bean Validation 注解，直接决定缺陷是否可测、可复用。
- **错误信息泄露**：直接把 `e.getMessage()` 返回给调用方可能暴露 SQL、类名、内部路径。
- **契约重复**：同一业务方法在多个接口（Feign 接口、`shop-service-api` 接口、Controller）中重复声明，容易漂移。

## 3. 项目中的实现链路

```text
HTTP 请求
  -> Controller 方法
       -> 业务校验: OrderParams.isEmpty()          // 手写校验，存在缺陷
       -> 业务处理: 可能 throw RuntimeException("库存扣减失败")
  -> 若抛异常: RestCtrlExceptionHandler(@RestControllerAdvice)
       -> @ExceptionHandler(Exception.class)
       -> 记录日志 + 返回 Result(code=500, codeMsg="执行失败", data=e.getMessage())
       -> HTTP 状态码仍为 200（因为方法返回的是普通对象，未标注 @ResponseStatus）
  -> 正常返回: Controller 直接返回 Product/User/Result/字符串
```

调用方（`shop-order` 的 V5/V6/V7）拿到的可能是三类东西：
1. 真实对象/`Result`；
2. 全局异常处理返回的 `Result(code=500)`（HTTP 200）；
3. Feign fallbackFactory 返回的哨兵值 `id=-1` / `code=1001`（HTTP 200）。

## 4. 关键选型与权衡

- 【代码事实】项目选择：**HTTP 200 + 业务码** 的响应模型 + `@RestControllerAdvice` 全局异常兜底 + 手写参数校验。
- **解决了什么**：
  - 前端/调用方只需解析一层 `Result`；
  - 异常不会以原始堆栈形式返回，至少包装成了 `Result`；
  - 成功/失败判定集中到 `code` 字段。
- **牺牲了什么 / 风险（这是本场景最有价值的部分）**：
  1. **HTTP 状态码失去意义**：全局异常处理返回 `Result` 但未设置 HTTP 状态，客户端看到的始终是 200。这与项目自身注释“统一返回状态码”的意图相悖——`HttpCode.FAILURE=500` 只是 body 里的一个数字。
  2. **Feign 会把错误当成功反序列化**：`Result` 是 200 响应体，Feign 不会走 `fallbackFactory`（fallback 只在连接失败/超时/异常状态/限流时触发），调用方必须显式检查 `code`。项目里 `V5` 检查了 `!= SUCCESS`，但如果下游抛的异常被全局处理器包成 `code=500`，Feign 依然拿到 200，`fallbackFactory` 不触发，语义就变成“静默的业务失败”。
  3. **两套错误码并存无规范**：`HttpCode` 只有 `200/500`，降级另用 `1001`，且 `1001` 没有常量定义（散落在 fallback 与业务判断里）。
  4. **`e.getMessage()` 直接外泄**：SQL 异常、空指针的类名等会返回给调用方。
  5. **对象型接口没有“未找到”表达**：`ProductController#getProduct` 查不到返回 `null`，Feign 侧收到空 body 后反序列化为 null，与“降级对象 `id=-1`”是两种含义，调用方需要同时处理 `null` 和 `-1`。
  6. **参数校验缺陷**：`OrderParams.isEmpty()` 第 29 行判断的是 `productId <= 0` 而不是 `userId <= 0`。当 `userId = 0` 或负数、`productId` 合法时，该方法返回 `false`（即“参数合法”），非法用户 ID 会一路传到 `userService.getUser(userId)`。这是可直接复现的缺陷。
- 【项目中未发现明确依据】没有错误码规范文档、没有异常分层（业务异常/系统异常基类）、没有 JSR-303 注解。

## 5. 关键工程实现

### 5.1 统一返回体

```java
@Data
@NoArgsConstructor
@AllArgsConstructor
public class Result<T> implements Serializable {
    private Integer code;     // 业务码：200 成功，500 失败，1001 降级
    private String  codeMsg;  // 描述
    private T       data;     // 载荷
}
```

要点：`data` 是泛型，成功时是业务对象，失败时是 `String`（异常信息）。调用方拿到的 `data` 类型不固定，需要先看 `code`。

### 5.2 全局异常处理

```java
@RestControllerAdvice
public class RestCtrlExceptionHandler {
    @ExceptionHandler(Exception.class)
    public Result<String> handleException(Exception e) {
        logger.error("服务器抛出了异常：{}", e);
        return new Result<>(HttpCode.FAILURE, "执行失败", e.getMessage());
        // 注意：返回普通对象，HTTP 状态码默认 200
    }
}
```

三个可改进点：
- 加 `@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)` 或返回 `ResponseEntity`，让 HTTP 语义正确；
- `data` 不要放 `e.getMessage()`，只放一个可对外的错误标识（如 `traceId` + 通用文案）；
- 增加更具体的 `@ExceptionHandler`（`IllegalArgumentException`、业务异常基类、`BlockException` 等），不要只用一个 `Exception` 兜底。

### 5.3 参数校验缺陷（可复现）

```java
public boolean isEmpty() {
    return (productId == null || productId <= 0) ||
           (userId == null || productId <= 0) ||   // BUG：应为 userId <= 0
           (count == null || count <= 0);
}
```

正确写法（任选其一）：

```java
// 方案一：修掉笔误
return (productId == null || productId <= 0)
    || (userId == null || userId <= 0)
    || (count == null || count <= 0);

// 方案二：改用 Bean Validation，把校验声明在字段上
public class OrderParams {
    @NotNull @Positive private Long productId;
    @NotNull @Positive private Long userId;
    @NotNull @Positive private Integer count;
}
// Controller: public String submitOrder(@Validated OrderParams p)
```

复现方式：`GET /order/submit_order?productId=1001&userId=0&count=1`。由于 `userId=0` 不触发 `isEmpty()`，会继续去查 id=0 的用户（查不到返回 null，再抛“未获取到用户信息”），错误信息指向下游而非参数本身，排障时容易被误导。

### 5.4 三类“失败”的识别成本

| 失败类型 | 响应形态 | 触发 fallback？ | 调用方如何识别 |
|---|---|---|---|
| 业务失败（库存不足等） | HTTP 200 + `code=500`（被全局处理器包装） | 否 | 检查 `code != 200` |
| 下游抛异常且未被全局处理 | HTTP 500 | 是 | fallbackFactory |
| 下游不可达/超时/被限流 | 无响应或 429/503 | 是 | fallbackFactory |
| 对象不存在 | HTTP 200 + 空 body | 否 | 判 null |
| 已降级 | HTTP 200 + `code=1001` 或 `id=-1` | —（结果本身） | 判 `1001` / `-1` |

这张表说明：调用方要正确处理一次调用，需要同时理解 5 种情况，这正是“契约不统一”的代价。

## 6. 踩坑、根因与排障

| 性质 | 现象 | 根因 | 项目处理 | 仍存缺口 | 验证或排查方法 |
|---|---|---|---|---|---|
| 已证实（代码） | 非法 `userId` 通过参数校验 | `isEmpty()` 第 29 行笔误 | 未处理 | 需修正或改注解校验 | 用 `userId=0` 请求 `submit_order`，观察报错位置 |
| 已证实（代码） | 业务失败返回 HTTP 200 | 全局处理器返回普通对象 | 未处理 | 应设置正确 HTTP 状态 | `curl -i` 查看状态行 |
| 潜在风险 | 内部异常信息泄露 | 直接把 `e.getMessage()` 放进 `data` | 未处理 | 需脱敏 | 制造 SQL 异常看响应体 |
| 潜在风险 | Feign 不触发降级却拿到 `code=500` | 错误被包装成 200 响应 | V5 检查 `code`，V6/V7 加 `-1` 判断 | 需统一“失败”定义 | 让下游抛业务异常，观察是否走 fallback |
| 潜在风险 | 调用方漏判 null 与 -1 | 对象型接口无“未找到”语义 | V6/V7 判 `-1`，未判 null（`getProduct` 可能返回 null） | 需 `Optional` 或空对象 | 用不存在的商品 id 调用 |
| 潜在风险 | 错误码无集中管理 | `1001` 散落硬编码 | 未处理 | 建错误码枚举 | 全局搜索 `1001` |

## 7. 可迁移的落地方案

【落地建议】

1. **先定契约三原则**：
   - HTTP 状态码表达传输/系统层结果（200/4xx/5xx/429）；
   - 业务码表达业务结果，且**必须集中定义**（错误码枚举 + 文案表）；
   - 响应体形状全局唯一（`code/message/data/requestId`）。
2. **异常分层**：定义 `BusinessException`（预期内、4xx）、`SystemException`（未预期、5xx）、`RemoteException`（下游失败）。全局处理器按类型映射，未预期异常只返回通用文案 + `requestId`。
3. **参数校验用 Bean Validation**：`@Validated` + 约束注解，全局处理 `MethodArgumentNotValidException`，输出字段级错误。手写 `isEmpty()` 只保留跨字段/跨对象规则。
4. **明确“失败可重试性”**：在响应中或错误码定义里标注是否可重试，供调用方与重试组件使用。
5. **Feign 调用方统一封装**：写一个 `ResultUtils.check(Result)`，非 200 即抛业务异常，避免每处手写判断；对象型接口统一返回 `Result<T>` 或约定“未找到”码。
6. **契约测试**：用 Spring Cloud Contract 或简单的 MockMvc 测试固定响应形状，防止漂移。
7. **可观测性**：每个响应带 `requestId`/`traceId`，异常日志与响应可关联。

### 最小闭环

`统一响应体 + 错误码枚举 + 异常分层 + Bean Validation + Feign 统一校验 + 契约测试`。

## 8. 替代方案与适用边界

- **HTTP 200 + 业务码**：前端友好、网关无需特殊处理；但监控/重试/告警需要额外解析，且容易像本项目一样把 HTTP 语义架空。
- **HTTP 状态码 + Problem Details（RFC 7807）**：更符合 HTTP 语义，适合开放 API 与多语言调用方；前端需区分处理。
- **gRPC 状态码**：内部服务间、强契约场景；本项目未使用。
- **GraphQL 错误数组**：BFF 场景。

判断依据：调用方是否多样、是否需要标准重试/监控语义、团队契约治理能力。**不建议**两种模型混用（本项目正踩在这个点上）。

## 9. 验收清单

- [ ] 所有接口成功/失败响应形状一致，且 HTTP 状态码语义正确。
- [ ] 业务码集中定义，无散落魔法值（如 `1001`）。
- [ ] 全局异常处理分层，未预期异常不泄露内部信息。
- [ ] 参数校验覆盖全部必填与范围，有单元测试或契约测试。
- [ ] Feign 调用方有统一的返回值校验封装，降级/null/业务失败均可识别。
- [ ] 存在“下游业务失败”与“下游不可达”两种演练，验证调用方行为符合预期。
- [ ] 响应带 `requestId`/`traceId` 可关联日志。
