# 11 成本治理：AI 调用配额的分布式限流

> 标签：成本治理 / 配额 / 分布式锁 / 并发控制 / Redis
>
> 证据根：`story-video-service/src/main/java/io/binghe/framework/service/{QuotaService,ImageService,VideoService,UserService}.java`

---

## 1. 场景与边界

平台每一次「生成章节 / 图片 / 视频」都在花钱（调大模型、调视频厂商）。必须给每个用户设**每日配额**，并在**并发请求**下也不能超额。

工程问题：

1. **配额模型**：按什么维度计（用户/日）、哪些能力计；
2. **并发安全**：多个请求同时「查剩余 → 扣减」会竞态超额，怎么防；
3. **每日重置**：跨天如何归零；
4. **非 HTTP 上下文**：流水线/异步线程里没有 SecurityContext，怎么处理；
5. **不可用/未配置**：没有配额记录时是「不限」还是「禁止」。

边界：
- 本文聚焦「配额检查 + 扣减 + 重置 + 并发控制」。
- 配额耗尽抛出的 429 与 AI 重试的交互见第 03 篇 §6.4。
- TTS 未纳入配额（见第 10 篇 §6.8）。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 查-改竞态 | 读剩余、判断、写回三步非原子，并发下会超额 |
| 跨进程 | 单机锁不够，多实例要分布式锁 |
| 锁的可靠性 | TTL、误删他人锁、锁过期 |
| 事务 | 扣减涉及「重置 + 累加」，应原子 |
| 上下文缺失 | 异步/流水线线程无当前用户 |
| 计费口径 | 哪些能力计、失败是否退还 |

---

## 3. 实现链路

### 3.1 配额检查与扣减（`checkAndConsume`）

```
checkAndConsume(userId, type, count)
  ├─ userId == null → return（不检查）
  ├─ lockKey = "story:quota:lock:" + userId
  ├─ SETNX lockKey "1" TTL=5s
  │    ├─ 成功 → 进入临界区
  │    └─ 失败 → sleep(100ms) 后重试一次 SETNX
  │         └─ 仍失败 → throw BizException(BIZ_ERROR, "操作过于频繁，请稍后重试")
  ├─ try: doCheckAndConsume(userId, type, count)
  └─ finally: DEL lockKey

doCheckAndConsume（@Transactional）
  ├─ select t_user_quota by userId
  ├─ quota == null → return（不限）
  ├─ 若 resetDate != today → 三个 used 归零，resetDate = today
  ├─ switch(type):
  │    chapter → 校验/累加 usedChapters（dailyChapterLimit）
  │    image   → 校验/累加 usedImages（dailyImageLimit）
  │    video   → 校验/累加 usedVideos（dailyVideoLimit）
  │    default → log.warn
  └─ updateById(quota)
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| Redis SETNX 分布式锁 | 简单、跨进程 | 需处理 TTL/误删/过期（见 §6.2/§6.3） |
| 锁粒度=用户 | 同用户串行，跨用户并行 | 单用户高频时锁竞争 |
| 锁内做 DB 扣减 | 临界区保护查改 | 锁持有时间受 DB 影响 |
| 每日按 `resetDate` 重置 | 无需定时任务 | 依赖服务器时区；跨天瞬间并发可能双扣 |
| `quota == null` 即不限 | 兼容历史/管理员用户 | **漏建记录即无限**（见 §6.4） |
| 失败一次只重试一回 | 避免长等待 | 高并发下直接报「操作过于频繁」 |

## 5. 关键工程实现

**（1）锁 + 扣减（`QuotaService.java:39-60`）**

```java
public void checkAndConsume(Long userId, String type, int count) {
    if (userId == null) return;
    String lockKey = LOCK_PREFIX + userId;
    boolean locked = Boolean.TRUE.equals(redisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL));
    if (!locked) {
        try { Thread.sleep(100); } catch (InterruptedException ignored) { Thread.currentThread().interrupt(); }
        locked = Boolean.TRUE.equals(redisTemplate.opsForValue().setIfAbsent(lockKey, "1", LOCK_TTL));
        if (!locked) throw new BizException(ErrorCode.BIZ_ERROR, "操作过于频繁，请稍后重试");
    }
    try { doCheckAndConsume(userId, type, count); }
    finally { redisTemplate.delete(lockKey); }
}
```

**（2）事务内查改（`QuotaService.java:62-102`）**

```java
@Transactional
protected void doCheckAndConsume(Long userId, String type, int count) {
    UserQuota quota = userQuotaMapper.selectOne(new LambdaQueryWrapper<UserQuota>().eq(UserQuota::getUserId, userId));
    if (quota == null) return;                                  // 无记录 → 不限制
    LocalDate today = LocalDate.now();
    if (!today.equals(quota.getResetDate())) {                  // 每日重置
        quota.setUsedChapters(0); quota.setUsedImages(0); quota.setUsedVideos(0);
        quota.setResetDate(today);
    }
    switch (type) {
        case "chapter" -> { ... used + count > limit → throw QUOTA_EXCEEDED; quota.setUsedChapters(used + count); }
        case "image"   -> { ... }
        case "video"   -> { ... }
        default -> log.warn("[Quota] Unknown type: {}", type);
    }
    userQuotaMapper.updateById(quota);
}
```

**（3）业务侧接入（`ImageService.java:59-66`）**

```java

} catch (Exception ignored) {
    // 非 HTTP 上下文（如流水线调用）跳过配额检查
```

## 6. 踩坑根因排障

### 6.1 【代码事实】`@Transactional` 被自调用绕过 → 扣减不在事务里

```java
public void checkAndConsume(...) { ... doCheckAndConsume(userId, type, count); ... }  // 同类调用
@Transactional protected void doCheckAndConsume(...) { ... }
```
`@Transactional` 基于代理，**同类内自调用不经过代理**，注解失效。于是「重置 used + 累加 + update」不是一个事务：若 `updateById` 失败，前面在内存里改的 `used` 不会写库（影响有限），但更重要的是——**它暴露了「以为有事务保护、实际没有」的认知风险**。与第 04/06 篇的 `@Async` 自调用是同一类问题。

**修复方向**：把 `doCheckAndConsume` 抽到独立 Bean，或改用 `TransactionTemplate` 显式开启事务。

### 6.2 【代码事实】锁没有「持有者标识」，可能误删他人的锁

`setIfAbsent(lockKey, "1", TTL)` 写入的是常量 `"1"`，`finally` 里**无条件 `delete(lockKey)`**。若发生：

1. 线程 A 拿到锁，DB 操作超过 5s → 锁自动过期；
2. 线程 B 拿到同一把锁；
3. A 操作完 `delete(lockKey)` → **删掉了 B 的锁**；

则临界区被破坏，B 之后的并发请求都能进。标准做法：锁值用唯一 token（UUID），释放时用 Lua 脚本「比较 token 再删」。

### 6.3 【代码事实】锁 TTL 固定 5s，可能短于临界区耗时

扣减要访问数据库，若 DB 慢或网络抖动 > 5s，锁提前失效，回到 §6.2 的问题。建议：TTL 适当放大 + 看门狗续期，或把临界区做轻（纯 Redis 计数）。

### 6.4 【代码事实】没有配额记录 = 永久不限

```java
if (quota == null) return; // 无配额记录，不限制
```
若用户记录被误删、或通过非 `createUser` 路径创建的用户没配额行，则**该用户没有任何限制**。对成本治理是反向风险。建议：无记录时按「默认配额」或「0（拒绝）」处理，并告警。

### 6.5 【代码事实】只会重试一次，高并发直接失败

锁竞争失败后 `sleep(100ms)` 只重试一次，随后抛 `操作过于频繁`。热点用户（批量生成）会频繁遇到失败。可改为有限次退避重试或排队。

### 6.6 【代码事实】配额提示可能显示「剩余 -N」

```java
throw new BizException(ErrorCode.QUOTA_EXCEEDED, "章节生成配额已用完（今日剩余 " + (limit - used) + " 次）");
```
当 `count > 1` 且 `used + count > limit` 时，`limit - used` 可能为负或与「count」不匹配，提示语会不合逻辑（如「剩余 -3 次」）。建议用 `Math.max(0, limit - used)`。

### 6.7 【代码事实】`chapter` 配额是「死配置」

`QuotaService` 支持 `case "chapter"`，但全仓**没有任何调用方**以 `"chapter"` 调用 `checkAndConsume`（只有 image / video）。因此 `dailyChapterLimit`（默认 50）**从不生效**，章节生成不受限。

### 6.8 【代码事实】TTS 不计配额

结合第 10 篇，TTS 也完全不走配额。若 TTS 按量计费，则是成本盲区。

### 6.9 【代码事实】每日重置用 `LocalDate.now()`，无显式时区

跨天判定依赖 JVM 默认时区；多实例时区不一致会出现「有的实例已重置、有的还没」的短暂不一致。

### 6.10 【代码事实】429 错误码与 AI 重试冲突

`QUOTA_EXCEEDED = 429`，而 `AiRetryTemplate.isRetryable` 把 429 当「限流」重试（第 03 篇 §6.4）。配额耗尽若发生在被重试包裹的链路里，会白白重试 3 次。建议配额用独立错误码。

### 6.11 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 并发下配额超额 | 锁过期/误删（§6.2/§6.3） | 唯一 token + Lua 释放 + TTL 续期 |
| 某用户完全不限 | 无配额记录（§6.4） | 无记录即按默认/拒绝 |
| 高频请求报「操作过于频繁」 | 只重试一次（§6.5） | 退避重试/排队 |
| 提示「剩余 -N 次」 | 未取 max（§6.6） | `Math.max(0, ...)` |
| 章节配额不生效 | 无调用方（§6.7） | 在章节生成处接入 |
| TTS 成本失控 | 不计配额（§6.8） | 接入配额 |
| 跨天配额错乱 | 时区不一致（§6.9） | 统一时区/Redis 计数 |
| 配额耗尽后拖 14s 才报错 | 429 被重试（§6.10） | 拆分错误码 |

## 7. 可迁移落地方案

`【落地建议】`

1. **配额扣减做原子操作**：优先用 Redis 原子计数（`INCR` + 上限判断 + Lua 保证原子），DB 只做异步落账；避免「分布式锁 + DB 查改」的重模式。
2. **分布式锁要用唯一 token + Lua 释放**，并考虑看门狗续期；否则宁可用 Redis 原子计数替代锁。
3. **无记录要有明确语义**：默认「按默认配额」或「拒绝」，绝不能「不限」。
4. **配额错误码独立**（不要复用 429），避免与「限流重试」语义冲突。
5. **覆盖所有计费能力**：章节、图片、视频、TTS、文本补全都应纳入。
6. **失败/取消要退还配额**：生成失败时把扣减的额度加回（或按「提交成功才计费」）。
7. **统一时区与重置口径**；跨天重置最好用 Redis TTL 或服务端统一时钟。
8. **可观测**：记录每个用户的用量与超限次数，便于成本分析。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 分布式锁 + DB 扣减（本方案） | 低并发、需强一致 | 高并发、热点用户 |
| Redis 原子计数（INCR/Lua） | 高并发、可容忍最终落账 | 需处理与 DB 对账 |
| 令牌桶/漏桶限流 | 限速（QPS）而非限额（日额度） | 精确日配额 |
| 网关/API 限流（Sentinel） | 全局保护 | 业务级配额粒度 |
| 计费系统（账单+扣费） | 精确计费 | 较重 |

## 9. 验收清单

- [ ] 并发请求下配额不超额（唯一 token 锁或原子计数）。

- [ ] `doCheckAndConsume` 在**真实事务**中执行。

- [ ] 配额错误码与重试语义不冲突。
