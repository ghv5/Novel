# 11 成本治理：AI 调用配额的分布式限流

> 标签：成本控制 / 配额 / 分布式锁 / 每日重置 / Redis

---

## 1. 场景与边界

AI 调用（尤其图片、视频、TTS）是**有成本**的。平台需要对每个用户做**每日配额**限制：章节数、图片数、视频数，用满即拒绝。

工程问题：
1. **并发安全**：同一用户并发请求不能「查一遍都通过，扣减时超卖」；
2. **每日重置**：跨天自动清零，而非定时任务；
3. **同源扣减**：无论从哪个入口（图片/视频/批量），都走同一套配额逻辑；
4. **优雅降级**：配额查询异常不应误伤正常业务。

边界：本场景讲配额；任务执行见第 04 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 并发扣减超卖 | 「读-改-写」非原子，需加锁 |
| 锁的粒度 | 按 userId 加锁，避免全局锁 |
| 每日重置无定时任务 | 用 `resetDate` 字段惰性判断 |
| 无配额记录 | 要有合理默认（不限/默认额度） |
| 配额异常处理 | 上游调用多包 `try/catch` 忽略异常 |

---

## 3. 实现链路

### 3.1 检查 + 扣减

```
checkAndConsume(userId, type, count)
  lockKey = "story:quota:lock:" + userId
  setIfAbsent(lockKey, "1", TTL)
    失败 → sleep 100ms 再试一次
    仍失败 → 抛「操作过于频繁」
  try:
     doCheckAndConsume(userId, type, count)   # @Transactional
  finally:
     redisTemplate.delete(lockKey)            # 释放锁
```

`doCheckAndConsume`：
```
quota = select by userId
if quota == null: return               # 无记录 → 不限
today = 今天
if !today.equals(quota.resetDate):     # 惰性重置
    usedChapters/Images/Videos = 0
    resetDate = today
switch(type):
    chapter: 校验并 +count
    image:   校验并 +count
    video:   校验并 +count
update
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| Redis 分布式锁 | 跨实例互斥，防超卖 | 锁 TTL 内进程崩溃则短暂阻塞 |
| 惰性每日重置 | 无需定时任务、无时区调度 | 依赖 `resetDate` 正确维护 |
| 按 userId 加锁 | 并发粒度细 | 高频同用户请求仍会串行 |
| 上游忽略异常 | 不误伤业务 | 配额失效时可能「免费放行」 |
| DB 存配额、Redis 加锁 | 持久化 + 并发控制分离 | 需 DB 事务配合 |

## 5. 关键工程实现

**（1）加锁-重试-拒绝（`QuotaService.java:42-53`）**
```java
String lockKey = LOCK_PREFIX + userId;
boolean locked = setIfAbsent(lockKey, "1", LOCK_TTL);
if (!locked) {
    Thread.sleep(100);
    locked = setIfAbsent(lockKey, "1", LOCK_TTL);
    if (!locked) throw new BizException(BIZ_ERROR, "操作过于频繁，请稍后重试");
}
```

**（2）惰性重置（`QuotaService.java:74-78`）**：`if (!today.equals(quota.getResetDate())) { 各 used 清零; resetDate = today; }`。【代码事实】

**（3）默认额度（`UserService.java:100-102`）**：新用户 50 章 / 200 图 / 100 视频每日。【代码事实】

## 6. 踩坑根因排障

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 配额超卖 | 扣减未在锁内/未事务 | 确认 `doCheckAndConsume` 在锁内且 `@Transactional` |
| 配额永远不重置 | `resetDate` 未更新或时区不一致 | 检查 `:74-78` |
| 用户被「误限流」 | 锁未释放（异常路径） | 已用 `finally`；检查 Redis 锁 TTL |
| 配额形同虚设 | 上游 `catch` 吞掉异常 | 检查 `ImageService.java:65-67`、`VideoService.java:49-51` |
| 无配额记录=不限 | `quota == null` 直接 return | 老用户迁移时需补记录 |
| 并发同用户仍慢 | 按 userId 串行 | 可接受；极端高频需令牌桶 |

## 7. 可迁移落地方案

`【落地建议】`

1. **配额的原子性**：用 Redis 锁或 Lua 脚本保证「检查+扣减」原子；锁按业务主体（userId）加，`finally` 释放并设 TTL。
2. **惰性重置**：存 `resetDate`，每次访问比对当天，跨天清零，避免调度复杂度。
3. **分层额度**：用户日额度 → 项目额度 → 全局额度，逐层校验。
4. **配额不足要可见**：返回明确错误码与剩余额度，便于前端提示。
5. **别吞配额异常**：配额服务故障应「失败关闭」（拒绝）还是「失败开放」（放行）要显式决策；当前实现是放行，成本敏感场景建议改为拒绝或告警。
6. **审计**：记录每次扣减的 type/count/时间，便于对账。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| Redis 锁 + DB 配额（本方案） | 中等并发、需持久化 | 超高频 |
| Redis 计数器 + Lua | 高并发原子扣减 | 需持久化明细 |
| 令牌桶/漏桶（Redis + Lua） | 限流（速率） | 限总量 |
| 网关限流（Sentinel） | 全局限流 | 按用户配额 |
