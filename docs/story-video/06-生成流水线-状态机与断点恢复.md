# 06 生成流水线：状态机与断点恢复

> 标签：工作流 / 有限状态机 / 断点续跑 / Redis 状态
>
> 证据根：`story-video-service/src/main/java/io/binghe/framework/service/pipeline/**`

---

## 1. 场景与边界

内容生成是一条**长流水线**：从小说到成片要经过 11 个阶段

```
小说 → 故事线 → 大纲 → 资产抽取 → 资产图 → 剧本 → 分镜 → 分镜图 → TTS → 视频 → 合成
```

工程问题：

1. **阶段顺序与合法性**：不能跳过前置阶段，也不能乱序；
2. **失败可重试**：某阶段失败后能从「失败步」重跑，而不是从头再来；
3. **状态可查询**：前端要能实时看到当前进度；
4. **状态要有权威源**：内存状态与持久化状态如何取舍。

边界：本文讲流水线**编排**；各阶段内部实现见第 04（视频）、第 10（TTS）等篇。本文 §6 的多处缺陷为**代码事实**，其运行期影响列入 §10 待确认。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 阶段多、迁移规则复杂 | 需显式建模允许的迁移，而非 if-else 铺开 |
| 迁移表要与实际调用一致 | 编排里写的 `startState/completeState` 必须都在白名单内（本项目未对齐，见 §6.2） |
| 失败恢复 | 需记住「失败的是哪一步」才能精确重试；且重试必须真的**重新执行**（见 §6.4） |
| 内存 vs 持久化 | 状态机对象在内存，多实例/重启会丢，需 Redis 兜底 |
| 长阶段轮询 | 视频阶段需等待异步任务完成，不能阻塞 `@Async` 线程池 |
| 并发项目 | 多个项目同时跑，状态机按项目隔离 |
| 异步代理 | 编排入口对执行方法的调用必须是跨 Bean（见 §6.1） |

## 3. 实现链路

### 3.1 状态机

`PipelineState` 定义全部阶段（24 个），`PipelineStateMachine` 用**白名单表**描述允许迁移：

```
PENDING
→ NOVEL_GENERATING → NOVEL_COMPLETE
→ STORYLINE_GENERATING → STORYLINE_COMPLETE
→ OUTLINE_GENERATING → (OUTLINE_REVIEWING) → OUTLINE_COMPLETE
→ ASSETS_EXTRACTING → ASSETS_IMAGE_GENERATING → ASSETS_COMPLETE
→ SCRIPT_GENERATING → SCRIPT_COMPLETE
→ STORYBOARD_GENERATING → STORYBOARD_COMPLETE
→ STORYBOARD_IMAGE_GENERATING → (IMAGE_QUALITY_CHECKING) → STORYBOARD_IMAGE_COMPLETE
→ TTS_GENERATING → TTS_COMPLETE
→ VIDEO_GENERATING → VIDEO_COMPLETE
→ COMPOSING → COMPOSE_COMPLETE → ALL_COMPLETE
（任一阶段可 → STEP_FAILED，STEP_FAILED 可回到任意 *_GENERATING / ASSETS_EXTRACTING / IMAGE_QUALITY_CHECKING / COMPOSING）
```

### 3.2 双存储（+ DB 兜底）

| 存储 | 内容 | 位置 |
| --- | --- | --- |
| 内存 `ConcurrentHashMap<projectId, PipelineStateMachine>` | 迁移校验 | `PipelineService.java:60` |
| Redis `PipelineStateStore` | 当前态 + 失败态，**TTL 2h** | `PipelineStateStore.java` |
| DB `t_task_list.state` | 兜底查询 | `PipelineService.updateTaskListState` |
| DB `t_task_list.checkpoint` | Agent 断点 JSON | `CheckpointManager.java` |
| DB `t_task_list` | 任务记录（PENDING/…/ALL_COMPLETE/STEP_FAILED） | `startPipeline` |

`getStatus` 的读取优先级：**内存 → Redis → DB**。

### 3.3 编排：11 个 `executeStep`，但前 3 步是「空检查」

| Step | startState → completeState | 实际动作 |
| --- | --- | --- |
| 1 小说生成 | `NOVEL_GENERATING → NOVEL_COMPLETE` | **仅 `selectCount` 检查是否存在并打日志**（不生成） |
| 2 故事线 | `STORYLINE_GENERATING → STORYLINE_COMPLETE` | **仅打日志**（不生成） |
| 3 大纲 | `OUTLINE_GENERATING → OUTLINE_COMPLETE` | **仅 `selectCount` 检查并打日志**（不生成） |
| 4 资产抽取 | `ASSETS_EXTRACTING → ASSETS_COMPLETE` | `assetsService.extractFromOutlines` |
| 5 资产图 | `ASSETS_IMAGE_GENERATING → ASSETS_COMPLETE` | 逐资产 `generateAssetImage` |
| 6 剧本 | `SCRIPT_GENERATING → SCRIPT_COMPLETE` | 逐大纲生成剧本 |
| 7 分镜 | `STORYBOARD_GENERATING → STORYBOARD_COMPLETE` | 逐剧本 `autoGenerate` |
| 8 分镜图 | `STORYBOARD_IMAGE_GENERATING → STORYBOARD_IMAGE_COMPLETE` | 对无图的资产补图 |
| 9 TTS（条件） | `TTS_GENERATING → TTS_COMPLETE` | `ttsEnabled=true` 时逐剧本 `generate` |
| 10 视频 | `VIDEO_GENERATING → VIDEO_COMPLETE` | 逐分镜 `submitGenerate` → `awaitVideoPending(30*60)` |
| 11 合成（条件） | `COMPOSING → COMPOSE_COMPLETE` | `autoCompose=true` 时逐剧本 `videoComposeService.submit` |

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 显式状态机（`allow` 表） | 迁移规则集中、可校验 | 维护迁移表，且**必须与编排保持一致**（本项目未对齐） |
| 内存状态机 + Redis 状态 | 校验快，Redis 兜底可查询 | 多实例下内存状态不共享，仅适合单实例 |
| `STEP_FAILED` 可回任意生成态 | 精确重试，无需从头 | 迁移表需同步维护 |
| `ScheduledExecutorService` 轮询 | 调度线程独立，不占用调度器 | **主线程仍 `future.get` 阻塞**（见 §6.3） |
| 2h TTL | 流水线最长耗时兜底 | 超过 2h 状态丢失 |
| `startBatch` 用 `commonPool` + `Semaphore` | 实现简单 | 占用公共 ForkJoinPool，缺乏隔离与可观测 |

## 5. 关键工程实现

**（1）迁移即校验（`PipelineStateMachine.java:67-78`）**

```java
public void transition(PipelineState target) {
    if (!canTransition(target)) {
        throw new IllegalStateException("非法状态转换: " + currentState + " → " + target);
    }
    this.currentState = target;
}
public boolean canTransition(PipelineState target) {
    Set<PipelineState> allowed = transitions.get(currentState);
    return allowed != null && allowed.contains(target);
}
```

**（2）单步执行：先迁入生成态、再迁到完成态（`PipelineService.java:299-315`）**

```java
transitionAndPersist(sm, projectId, startState);
emitEvent(projectId, "stepStart", ...);
try {
    action.run();
    transitionAndPersist(sm, projectId, completeState);
    emitEvent(projectId, "stepComplete", ...);
} catch (Exception e) {
    transitionAndPersist(sm, projectId, PipelineState.STEP_FAILED);
    stateStore.saveFailedStep(projectId, startState);   // 记住失败步
    updateTaskListState(projectId, PipelineState.STEP_FAILED);
    emitEvent(projectId, "stepFailed", ...);
    throw e;                                            // 冒泡到最外层，终止整条流水线
}
```

**（3）视频阶段「非阻塞」轮询（`PipelineService.java:264-297`）**：`scheduleWithFixedDelay(..., 0, 10, SECONDS)` 每 10s 查 `countPending`，主线程 `future.get(timeoutSeconds + 30, SECONDS)` 等待。

**（4）编辑器兼容的状态查询（`PipelineService.java:408-443`）**：内存 → Redis → DB，DB 值非法时回落 `PENDING`。

## 6. 踩坑根因排障

### 6.1 【代码事实 + 工程推断】`@Async` 被自调用绕过 → 流水线可能同步阻塞

`startPipeline` 在**同一个 Bean 内**直接调用 `executePipelineAsync`：

```java
executePipelineAsync(projectId, request);   // PipelineService.java:84
@Async public void executePipelineAsync(...) { ... }
```
`@Async` 基于代理，自调用不经过代理 → 注解不生效。【工程推断】HTTP 的 `/start` 请求会**同步执行完整条流水线**（含最长 30 分钟的视频等待），请求必然超时。与第 04 篇 `VideoService` 是同一类问题。

### 6.2 【代码事实】迁移表与编排不一致 → 流水线在第 4 步必挂

看 `PipelineStateMachine.defineTransitions()` 中与资产相关的白名单：

```java
allow(PipelineState.OUTLINE_COMPLETE, PipelineState.ASSETS_EXTRACTING);
allow(PipelineState.ASSETS_EXTRACTING, PipelineState.ASSETS_IMAGE_GENERATING, PipelineState.STEP_FAILED);
allow(PipelineState.ASSETS_IMAGE_GENERATING, PipelineState.ASSETS_COMPLETE, PipelineState.STEP_FAILED);
allow(PipelineState.ASSETS_COMPLETE, PipelineState.SCRIPT_GENERATING);
```

而编排实际做的是：

- **Step 4**：`executeStep(sm, ..., ASSETS_EXTRACTING, ASSETS_COMPLETE, ...)` → 需要 `ASSETS_EXTRACTING → ASSETS_COMPLETE`，**不在白名单**；
- **Step 5**：`executeStep(sm, ..., ASSETS_IMAGE_GENERATING, ASSETS_COMPLETE, ...)` → 先需要 `ASSETS_COMPLETE → ASSETS_IMAGE_GENERATING`（第 4 步成功后的当前态是 `ASSETS_COMPLETE`），**也不在白名单**。

**后果**：Step 4 的 `action.run()` 执行完后，第 306 行 `transitionAndPersist(..., ASSETS_COMPLETE)` 抛 `IllegalStateException("非法状态转换: ASSETS_EXTRACTING → ASSETS_COMPLETE")`，被 `executeStep` 的 catch 捕获 → 置 `STEP_FAILED` 并冒泡 → 整条流水线终止。即**流水线跑到资产阶段就稳定失败**。

同一份表里还有一处：`VIDEO_COMPLETE` 只允许 → `COMPOSING`（第 49 行），而编排在 `autoCompose=false` 时直接 `transitionAndPersist(..., ALL_COMPLETE)`（第 249 行）→ 需要 `VIDEO_COMPLETE → ALL_COMPLETE`，**不在白名单** → 同样抛非法迁移。即**关闭合成开关反而会让流水线失败**。

**修复方向**：让「编排声明的 start/complete 迁移」与「白名单」由同一处定义派生（例如用枚举对声明合法迁移），或至少在启动时对全部 `executeStep` 参数做一次自检。

### 6.3 【代码事实】`awaitVideoPending` 仍阻塞流水线线程

方法注释写「不占用 @Async 线程池」，但实现里主线程执行 `future.get(timeoutSeconds + 30, TimeUnit.SECONDS)`：

```java
// 阻塞等待轮询完成，但轮询本身在独立调度线程
future.get(timeoutSeconds + 30, TimeUnit.SECONDS);
```
调度线程确实独立，但**调用 `awaitVideoPending` 的流水线线程被阻塞**，与「非阻塞」宣传不符（注释后半句已承认）。

### 6.4 【代码事实】`retryStep` 只回退状态、不重新执行

```java
public void retryStep(Long projectId) {
    ...
    PipelineState failedState = stateStore.getFailedStep(projectId);
    if (failedState != null) {
        PipelineStateMachine sm = new PipelineStateMachine();
        sm.setCurrentState(PipelineState.STEP_FAILED);
        sm.transition(failedState);
        stateMachines.put(projectId, sm);
        stateStore.saveState(projectId, failedState);
    }
    // ← 没有任何 executePipelineAsync / 重新编排调用
}
```
`retryStep` 把状态机「摆」回失败步，却**没有触发后续执行**。前端点「重试」后状态会停在失败步且不会继续跑。`skipStep`、`approveReview` 同样是只打日志的空壳（`PipelineService.java:390-406`）。

### 6.5 【代码事实】`terminate` 无法中断正在跑的流水线

`terminate` 只 `stateMachines.remove` + `stateStore.remove`，正在执行的 `executePipelineAsync` 线程不受影响，后续 `transitionAndPersist` 会发现内存状态机缺失而 NPE/静默失败。

### 6.6 【代码事实】`t_task_list.state` 取值与断点查询口径不一致

`startPipeline` 写的是 `PipelineState.PENDING.name()`（全大写下划线，如 `ASSETS_COMPLETE`），而 `CheckpointManager.findGenerating` 等处查询的是 `state="generating"` 这类小写值 —— 两套口径需核对，否则断点恢复查不到记录。

### 6.7 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| `/start` 请求超时 | `@Async` 自调用（§6.1） | 抽独立 Bean / 自注入 |
| 流水线跑到资产阶段就失败 | 迁移表缺 `ASSETS_*→ASSETS_COMPLETE`（§6.2） | 补白名单或改编排 |
| `autoCompose=false` 反而失败 | `VIDEO_COMPLETE→ALL_COMPLETE` 未授权（§6.2） | 补白名单 |
| 点重试后不动 | `retryStep` 不重跑（§6.4） | 补调用 |
| 点终止仍继续跑 | `terminate` 不中断（§6.5） | 加中断标志/Cancellation |
| 多实例下状态不一致 | 内存状态机不跨实例 | 只依赖 Redis 或加分布式协调 |
| 状态突然查不到 | Redis TTL(2h) 过期 | 延长 TTL 或持久化 DB |
| 前端进度不动 | 订阅的主题错了 | 实际主题是 `/topic/agent/pipeline/{projectId}/event`（不是 `/topic/pipeline/...`） |
| 视频阶段卡住 | 轮询超时 + `countPending` 不归零 | 查被静默丢弃的视频任务（见第 04 篇 §6.3） |

## 7. 可迁移落地方案

`【落地建议】`

1. **状态显式化**：所有阶段定义成枚举，迁移写成「白名单表」，非法迁移抛错。
2. **迁移表与编排同源**：让 `executeStep` 的 start/complete 参数**由迁移表校验**，或在应用启动时对全部步骤做一次「可达性自检」，避免「表对不上代码」。
3. **双写状态**：内存（快速校验）+ Redis（可查询/兜底），键 `pipeline:{id}:state` 与 `:failed`。
4. **精确重试**：单独记录「失败步」，重试从失败步续跑——**并且一定要触发重新执行**。
5. **长阶段异步 + 调度轮询**：不要用业务线程阻塞等待；用「提交 + 回调/事件」而非 `future.get`。
6. **插入审核点**：在关键阶段设 `*_REVIEWING` 态，支持人工/质量门控，并让 `approveReview` 真正放行。
7. **终止要能取消**：为运行中的流水线维护 `CancellationToken`，`terminate` 时置位并中断等待。
8. **可考虑升级**：任务量大时迁移到**持久化工作流引擎**（Temporal/Cadence/XXL-Job），天然支持重试、回放、多实例、取消。

---

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 显式状态机 + Redis（本方案） | 单体、阶段固定的流水线 | 多实例、动态分支、需要取消/回放 |
| 工作流引擎（Temporal/Flowable） | 复杂编排、需持久化与重试 | 引入较重 |
| 状态机库（Spring Statemachine） | 需要标准状态机能力 | 增加框架耦合 |
| DB 状态字段 + 定时扫描 | 极简实现 | 实时性差 |
| 事件驱动（阶段完成发事件） | 松耦合、易扩展 | 需 MQ 与幂等设计 |

## 9. 验收清单

- [ ] 合法迁移放行、非法迁移被拒。
- [ ] 全部 `executeStep` 的 start/complete 迁移**全部**通过白名单（含资产阶段、`autoCompose=false`）。
- [ ] 任一阶段失败进入 `STEP_FAILED` 并记录失败步。
- [ ] `retryStep` **真正重新执行**并恢复成功。
- [ ] `skipStep` / `approveReview` 有真实语义（非空壳）。
- [ ] `terminate` 能中断运行中的流水线。
- [ ] `getStatus` 内存优先、Redis 兜底、DB 最后。
- [ ] 完成后 `ALL_COMPLETE` 且清理内存状态。
- [ ] 视频阶段不阻塞流水线线程（或明确接受阻塞并配置足够超时）。
- [ ] 进度事件推送到 `/topic/agent/pipeline/{projectId}/event`。
- [ ] Redis 状态 TTL 与预期流水线时长匹配。
