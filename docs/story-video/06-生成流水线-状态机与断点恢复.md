# 06 生成流水线：状态机与断点恢复

> 标签：工作流 / 有限状态机 / 断点续跑 / Redis 状态

---

## 1. 场景与边界

内容生成是一条**长流水线**：从小说到成片要经过 11 个阶段（小说生成 → 故事线 → 大纲 → 资产抽取 → 资产图 → 剧本 → 分镜 → 分镜图 → TTS → 视频 → 合成）。

工程问题：
1. **阶段顺序与合法性**：不能跳过前置阶段，也不能乱序；
2. **失败可重试**：某阶段失败后能从「失败步」重跑，而不是从头再来；
3. **状态可查询**：前端要能实时看到当前进度；
4. **状态要有权威源**：内存状态与持久化状态如何取舍。

边界：本场景讲流水线编排；各阶段的内部实现分散在第 04（视频）、第 10（TTS）等篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 阶段多、迁移规则复杂 | 需显式建模允许的迁移，而非 if-else 铺开 |
| 失败恢复 | 需记住「失败的是哪一步」才能精确重试 |
| 内存 vs 持久化 | 状态机对象在内存，多实例/重启会丢，需 Redis 兜底 |
| 长阶段轮询 | 视频阶段需等待异步任务完成，不能阻塞 `@Async` 线程池 |
| 并发项目 | 多个项目同时跑，状态机按项目隔离 |

---

## 3. 实现链路

### 3.1 状态机

`PipelineState` 定义了全部阶段与终态：

```
PENDING
→ NOVEL_GENERATING → NOVEL_COMPLETE
→ STORYLINE_GENERATING → STORYLINE_COMPLETE
→ OUTLINE_GENERATING → (OUTLINE_REVIEWING) → OUTLINE_COMPLETE
→ ASSETS_EXTRACTING → ASSETS_IMAGE_GENERATING → ASSETS_COMPLETE
→ SCRIPT_GENERATING → SCRIPT_COMPLETE
→ STORYBOARD_GENERATING → STORYBOARD_COMPLETE
→ STORYBOARD_IMAGE_GENERATING → (IMAGE_QUALITY_CHECKING) → STORYBOARD_IMAGE_COMPLETE
→ TTS_GENERATING → TTS_COMPLETE
→ VIDEO_GENERATING → VIDEO_COMPLETE
→ COMPOSING → COMPOSE_COMPLETE → ALL_COMPLETE
（任一阶段可 → STEP_FAILED，STEP_FAILED 可回到任意 *_GENERATING）
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 显式状态机（`allow` 表） | 迁移规则集中、可校验 | 维护迁移表 |
| 内存状态机 + Redis 状态 | 校验快，Redis 兜底可查询 | 多实例下内存状态不共享，仅适合单实例 |
| `STEP_FAILED` 可回任意生成态 | 精确重试，无需从头 | 可能漏掉阶段间依赖 |
| 专用 `ScheduledExecutorService` 轮询 | 不占用 `@Async` 线程池 | 多一个线程池 |
| 2h TTL | 流水线最长耗时兜底 | 超过 2h 状态丢失 |

## 5. 关键工程实现

**（1）迁移即校验（`PipelineStateMachine.java:68-78`）**：每次 `transition(target)` 先 `canTransition`，非法迁移直接拒绝。【代码事实】

**（2）失败可精确重试（`PipelineService.java:385-400`）**：
```java
PipelineState failedState = stateStore.getFailedStep(projectId);
PipelineStateMachine sm = new PipelineStateMachine();
stateMachines.put(projectId, sm);
stateStore.saveState(projectId, failedState);
// 从 failedState 继续执行
```
`【工程推断】` 重建状态机后需把 `currentState` 设为失败态，否则 `transition` 会被拦截。

**（3）视频阶段不阻塞线程池（`PipelineService.java:67,273`）**：用独立 `ScheduledExecutorService` 每 10s 轮询 `countPending`，避免占满 `@Async` 线程。

**（4）Review 门控**：`OUTLINE_REVIEWING` / `IMAGE_QUALITY_CHECKING` 提供人工/质量审核插入点，`approveReview` 放行。【代码事实】

## 6. 踩坑根因排障

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 重试后仍停在失败态 | 重建状态机未设置 `currentState` | 检查 `retryStep` 是否 set state |
| 多实例下状态不一致 | 内存状态机不跨实例 | 多实例需只依赖 Redis，或加分布式协调 |
| 状态突然查不到 | Redis TTL(2h) 过期 | 长任务需延长 TTL 或持久化到 DB |
| 迁移被拒 | 目标态不在 `allow` 列表 | 对照 `PipelineStateMachine.java:28-61` |
| 视频阶段卡住 | 轮询超时 | 检查 `awaitVideoPending` 的超时参数 |
| 前端进度不动 | `emitEvent` 未推或订阅主题不对 | 对照 `/topic/pipeline/{projectId}` |

## 7. 可迁移落地方案

`【落地建议】`

1. **状态显式化**：所有阶段定义成枚举，迁移写成「白名单表」，非法迁移抛错。
2. **双写状态**：内存（快速校验）+ Redis（可查询/兜底），键 `pipeline:{id}:state` 与 `:failed`。
3. **精确重试**：单独记录「失败步」，重试从失败步续跑，而非整条重来。
4. **长阶段异步 + 调度轮询**：不要用业务线程阻塞等待。
5. **插入审核点**：在关键阶段设 `*_REVIEWING` 态，支持人工/质量门控。
6. **可考虑升级**：任务量大时迁移到**持久化工作流引擎**（Temporal/Cadence/XXL-Job），天然支持重试、回放、多实例。

---

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 显式状态机 + Redis（本方案） | 单体、阶段固定的流水线 | 多实例、动态分支 |
| 工作流引擎（Temporal/Flowable） | 复杂编排、需持久化与重试 | 引入较重 |
| 状态机库（Spring Statemachine） | 需要标准状态机能力 | 增加框架耦合 |
| DB 状态字段 + 定时扫描 | 极简实现 | 实时性差 |

## 9. 验收清单

- [ ] 合法迁移放行、非法迁移被拒。
- [ ] 任一阶段失败进入 `STEP_FAILED` 并记录失败步。
- [ ] `retryStep` 从失败步续跑并恢复成功。
- [ ] `getStatus` 内存优先、Redis 兜底。
- [ ] 完成后 `ALL_COMPLETE` 且清理内存状态。
- [ ] 视频阶段不阻塞 `@Async` 主流程。
- [ ] 进度事件推送到 `/topic/pipeline/{projectId}`。
- [ ] Redis 状态 TTL 与预期流水线时长匹配。
