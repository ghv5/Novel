# 02 AI 模型接入：配置驱动的多厂商路由与密钥加密

> 标签：多厂商适配 / 工厂 / 配置化 / AES / 密钥治理

---

## 1. 场景与边界

平台要接入 **文本 / 图片 / 视频 / TTS** 四类、多家厂商模型（DeepSeek、通义千问、豆包、智谱、OpenAI、Gemini、Anthropic、xAI；Vidu、RunningHub、火山、Kling、Wan、Apimart……）。

业务代码**不应硬编码厂商**，只应表达「我要一个用于 X 用途的文本模型」。因此需要一层**配置驱动的路由**：业务写 `functionKey` → 查映射表 → 拿到某条厂商配置 → 由工厂造出对应 Provider。

边界：本场景只讲**「如何选到并造出 Provider」**与**「密钥如何安全落库」**；具体调用/重试/降级见第 03、04 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 厂商差异大但接口要统一 | 用 `TextAiProvider`/`ImageAiProvider`/`VideoAiProvider`/`TtsAiProvider` 四个接口收敛 |
| 用途与厂商解耦 | 引入 `functionKey → configId` 映射（`t_ai_model_map`），业务不感知厂商 |
| 密钥不能明文落库 | API Key 存库前 AES 加密，列表接口返回脱敏 |
| 动态换厂商不改代码 | 工厂按 `manufacturer` 字段 `switch` 到具体 Provider |
| 连通性要能自测 | 提供 `testConnectivity` 用真实配置探测 |

---

## 3. 实现链路

### 3.1 路由链

```
业务: aiProviderService.getTextProvider("videoPromptPolish")
  → resolveConfig(functionKey)
      → t_ai_model_map where key = functionKey  → 得到 configId
      → t_config selectById(configId)           → 得到厂商/模型/apiKey
  → TextAiProviderFactory.create(config)
      → AesUtil.decrypt(apiKey)
      → switch(manufacturer) → new XxxProvider(...)
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 接口抽象 + 工厂 `switch` | 新增厂商只加一个 `case` 和类 | 工厂随厂商增多而膨胀，可用注册表替换 |
| 映射表与配置表分离 | 用途（functionKey）与连接信息（config）解耦，可复用同一配置 | 多一次查询 |
| 每次调用实时 `resolveConfig` | 改配置即时生效，无需重启 | 每调用多两次 DB 查询，可加缓存 |
| AES/CBC 固定 IV（取密钥前 16 字节） | 实现简单 | CBC 固定 IV 不够安全，建议 GCM + 随机 IV |

## 5. 关键工程实现

**（1）用途路由（`AiProviderService.java:55-63`）**
```java
AiModelMap mapping = aiModelMapMapper.selectOne(
    new LambdaQueryWrapper<AiModelMap>().eq(AiModelMap::getKey, functionKey));
if (mapping == null) throw new BizException(ErrorCode.NOT_FOUND, "未配置功能映射: " + functionKey);
Config config = configMapper.selectById(mapping.getConfigId());
if (config == null) throw new BizException(ErrorCode.NOT_FOUND, "模型配置不存在: configId=" + mapping.getConfigId());
return config;
```

**（2）密钥落库即加密（`ConfigService.java:47`）**：`AesUtil.encrypt(request.getApiKey())`；读取时 `decrypt` 再 `maskApiKey`。【代码事实】

**（3）工厂按厂商分发（`TextAiProviderFactory.java:38-47`）**：`switch` 到各 Provider，`default` 落到通用的 `OpenAiCompatibleProvider`，兼容任意 OpenAI 协议厂商。【代码事实】

## 6. 踩坑根因排障

> ⚠️ 本场景集中了本项目的**多个真实配置坑**，迁移时务必逐条核对。

| 现象 | 根因 | 证据 |
| --- | --- | --- |
| OSS 配置写了却不生效 | `OssService` 读 `story.oss.*`，而 yml 配的是 `video.oss.*` | `OssService.java:28-40` vs `application.yml:47-51` |
| 跨域配置不生效 | `CorsConfig` 读 `story.cors.allowed-origins`，ymd 配 `video.cors.allowed-origins` | `CorsConfig.java:22` vs `application.yml:56-57` |
| `video.aes.key` 改了没用 | `AesUtil.setKey()` **全仓无调用方**，实际用类内硬编码密钥 | `AesUtil.java:13`（硬编码）、`AesUtil.java:15-16`（setKey 无调用） |
| 换厂商后返回空/报错 | `t_ai_model_map.key` 与业务传入的 `functionKey` 不一致 | `AiProviderService.java:57` |
| `spring.jackson.*` 配置无效 | `JacksonConfig` 自建 `ObjectMapper` 覆盖自动配置 | `story-video-config/.../JacksonConfig.java` |

`【工程推断】` 前三条中，前缀不一致与 `setKey` 未调用会导致**静默降级**：不报错但用默认值，排查时优先核对「配置键名」与「注入点」是否一一对应。

---

## 7. 可迁移落地方案

`【落地建议】`

1. **两层配置模型**：`用途(functionKey) → 配置(configId) → 连接信息`。业务永远只写用途。
2. **接口 + 工厂 + 兜底**：每个能力一个接口，工厂 `switch` 厂商，`default` 落到 OpenAI 兼容实现，覆盖长尾厂商。
3. **密钥加密落库 + 脱敏出参**：写入 `encrypt`，列表 `mask`，测试连通性用解密后的值。
4. **配置键统一前缀**：全项目用**同一个顶层命名空间**（如 `app.*`），并用配置元数据（`@ConfigurationProperties`）校验，避免 `story.*`/`video.*` 混用。
5. **加解密升级**：`AES/GCM/NoPadding` + 随机 IV + 密钥来自 KMS/环境变量，`setKey` 在启动时从配置注入。

---

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| DB 配置 + 工厂（本方案） | 多厂商、需在线改配置 | 固定单一厂商的小系统 |
| Spring `@ConditionalOnProperty` 装配 | 启动期确定厂商 | 运行期动态切换 |
| 注册表 Map（`manufacturer → Provider`） | 厂商多、避免 `switch` 膨胀 | — |
| 网关/中间层统一转发 | 多服务共用模型配置 | 单体应用 |

## 9. 验收清单

- [ ] 新增一个 `functionKey` 只需配置映射，无需改代码。
- [ ] `t_config.api_key` 在库中为密文。
- [ ] 配置列表接口返回 `maskApiKey` 结果，绝不明文。
- [ ] `testConnectivity` 对正确/错误密钥分别返回成功/失败。
- [ ] 各 `@Value` 前缀与 `application.yml` 完全一致（重点核对 `story.*` vs `video.*`）。
- [ ] `AesUtil.setKey` 在启动时被调用且密钥来自配置。
- [ ] 未配置映射时返回明确业务错误码，而非空指针。
