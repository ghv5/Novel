# 02 AI 模型接入：配置驱动的多厂商路由与密钥加密

> 标签：多厂商抽象 / 配置驱动路由 / 密钥加密 / 工厂模式
>
> 证据根：`story-video-ai/src/main/java/io/binghe/framework/ai/{service,factory,utils}/**` + `story-video-service/.../ConfigService.java`

---

## 1. 场景与边界

平台要接入 9 家文本、5 家图像、7 家视频、4 家 TTS 厂商，且**同一业务动作（如"写大纲"）在不同客户处可能配不同的模型**。硬编码厂商必然失控。

工程问题：

1. **解耦**：业务代码只声明"我要做 X"，不关心后端是哪家模型；
2. **可配置**：运营能在界面上改"这个功能用哪个模型、哪个 key"；
3. **多厂商差异**：请求/响应格式不同，怎么统一；
4. **密钥安全**：API Key 不能明文落库；
5. **运行时切换**：改配置后无需重启即生效。

边界：
- 本文聚焦"功能标识 → 模型配置 → Provider 实例"的路由链，以及密钥加密。
- 具体 Provider 的请求构造与重试见第 03 篇。
- 各 Provider 支持的模型清单见 `Constants` 与 `TextModelRegistry`。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 两层间接 | "功能 key" 与 "模型配置" 是多对一关系，需中间映射表 |
| 差异收敛 | 厂商协议不同，但大多数可归一为 OpenAI 兼容协议 |
| 密钥加密 | 落库加密、出参脱敏、运行时解密 |
| 密钥注入 | 加密用的主密钥必须来自配置，**不能硬编码**（本项目未做到，见 §6.1） |
| 保留字 | `t_ai_model_map.key` 的 `key` 是 SQL 保留字 |
| 配置变更原子性 | 全量替换映射时应在一个事务内 |
| 空制造商 | `manufacturer` 为空时工厂如何兜底 |

---

## 3. 实现链路

### 3.1 路由链：业务只给 `functionKey`

```
业务调用：aiProviderService.getTextProvider("novel-main")
  └─ resolveConfig("novel-main")
       ├─ t_ai_model_map where `key` = 'novel-main'  → 取 config_id
       │    （找不到 → BizException NOT_FOUND「未配置功能映射」）
       └─ t_config by id                             → 取加密的 apiKey / manufacturer / model / baseUrl
         （找不到 → BizException NOT_FOUND「模型配置不存在」）
  └─ textFactory.create(config)
       ├─ apiKey 空 → BizException AI_CALL_FAILED「API Key 不能为空」
       ├─ copyWithDecryptedKey(config)  ← AES 解密，不改原对象
       └─ switch(manufacturer) → 对应 Provider（default → OpenAiCompatibleProvider）
```

### 3.2 数据模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `t_config` | `id / type / name / manufacturer / model / api_key(Base64 密文) / base_url` | 一个具体厂商模型配置 |
| `t_ai_model_map` | `id / config_id / name / `key`` | 功能标识 → 配置，多对一 |

### 3.3 密钥生命周期

```
写入：ConfigService.create/update → AesUtil.encrypt(apiKey) → 存 Base64 密文
读出（列表）：toResponse → AesUtil.decrypt → AesUtil.maskApiKey → 只返回掩码（如 sk-a****1234）
运行时：Factory.copyWithDecryptedKey → AesUtil.decrypt → 给 Provider 用
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| `functionKey → t_ai_model_map → t_config` 两层 | 一个模型可服务多功能；改功能不动业务代码 | 多一次查询、多一张表 |
| 工厂 + switch 厂商 | 集中、显式、易读 | 新增厂商要改 switch 与 Constants |
| default 走 `OpenAiCompatibleProvider` | 新兼容厂商"不注册也能用" | 非兼容厂商需显式分支 |
| 每次调用都查库 + 解密 + new Provider | 改配置即时生效 | 无缓存，DB/解密开销在热路径 |
| `copyWithDecryptedKey` 不改原对象 | 避免污染缓存/实体 | 每次多一次对象拷贝 |
| AES/CBC + 固定 IV + Base64 | 简单 | **IV 固定 = 确定性加密，安全性弱**（见 §6.2） |
| 出参只给掩码 | 防密钥泄露 | 前端无法回显完整 key（预期行为） |

## 5. 关键工程实现

**（1）路由解析（`AiProviderService.java:54-65`）**

```java
private Config resolveConfig(String functionKey) {
    AiModelMap mapping = aiModelMapMapper.selectOne(
            new LambdaQueryWrapper<AiModelMap>().eq(AiModelMap::getKey, functionKey));
    if (mapping == null) throw new BizException(ErrorCode.NOT_FOUND, "未配置功能映射: " + functionKey);
    Config config = configMapper.selectById(mapping.getConfigId());
    if (config == null) throw new BizException(ErrorCode.NOT_FOUND, "模型配置不存在: configId=" + mapping.getConfigId());
    return config;
}
```

**（2）厂商分派 + 解密（`TextAiProviderFactory.java:31-60`）**

```java
public TextAiProvider create(Config config) {
    if (config.getApiKey() == null || config.getApiKey().isBlank())
        throw new BizException(ErrorCode.AI_CALL_FAILED, "API Key 不能为空");
    Config decrypted = copyWithDecryptedKey(config);
    return switch (config.getManufacturer()) {
        case Constants.MODEL_DEEPSEEK -> new DeepSeekProvider(decrypted, httpClient, objectMapper, registry);
        ... // qwen / doubao / zhipu / openai / gemini / anthropic / xai
        default -> new OpenAiCompatibleProvider(decrypted, httpClient, objectMapper, registry);
    };
}
```

**（3）加密（`AesUtil.java:19-33`）**

```java
public static String encrypt(String plainText) {
    byte[] keyBytes = padKey(aesKey).getBytes(StandardCharsets.UTF_8);
    SecretKeySpec secretKey = new SecretKeySpec(keyBytes, "AES");
    byte[] iv = Arrays.copyOf(keyBytes, 16);            // IV = key 前 16 字节（固定）
    Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
    cipher.init(Cipher.ENCRYPT_MODE, secretKey, new IvParameterSpec(iv));
    return Base64.getEncoder().encodeToString(cipher.doFinal(plainText.getBytes(UTF_8)));
}
```

**（4）保留字转义（`AiModelMap.java:31`）**

```java
@TableField("`key`")
private String key;
```

**（5）映射全量替换（`ConfigService.java:78-90`）**：`@Transactional` + `delete(null)` + 逐条 insert，保证替换原子性。

## 6. 踩坑根因排障

### 6.1 【代码事实】`AesUtil.setKey()` 无调用方 → `video.aes.key` 完全不生效

```java
private static String aesKey = "video-aes-secret-key-32b!0000";   // 硬编码
public static void setKey(String key) { aesKey = padKey(key); }   // 全仓无调用
```
`application.yml` 配了 `video.aes.key`，但**没有任何代码把它传给 `AesUtil.setKey`**（未找到 `@PostConstruct`/配置类调用）。后果：

- 实际加解密始终用硬编码密钥；
- 生产若要轮换密钥（改 yml），**密文仍然用旧硬编码密钥**，改了也没用；
- 更危险的是：**密文可被任何拿到源码的人解密**。

**排查**：全仓搜索 `AesUtil.setKey` / `aes.key` 的消费点。**修复**：加一个 `@Configuration` 在启动时 `AesUtil.setKey(${video.aes.key})`。

### 6.2 【代码事实】固定 IV 使 AES 成为「确定性加密」

```java
byte[] iv = Arrays.copyOf(keyBytes, 16);   // IV 直接取自密钥，恒定
```
同一密钥下，**相同明文永远产生相同密文**。可以据此做「相同 API Key 探测」，也不符合 CBC 的随机 IV 要求。此外 CBC 无完整性校验（无 HMAC/认证），密文被篡改无法发现。**建议**：随机 IV 并随密文一起存储（如 `Base64(iv + ciphertext)`），或改用 AES-GCM。

### 6.3 【代码事实】「连通性测试」有真实副作用和成本

`testConnectivity` 不只是探测，而是**真的发起一次生成**：

```java
case "image" -> provider.generate(ImageRequest.builder().prompt("test").width(64).height(64).build());
case "video" -> provider.createTask(VideoRequest.builder().prompt("test").build());   // 真的创建视频任务！
```
- 图像会真的生成一张 64×64 图（可能计费）；
- 视频会**真的提交一个视频生成任务**（按分钟计费的厂商会直接扣费），且 `createTask` 返回的 taskId 被丢弃、无人轮询。

**建议**：改用厂商的轻量探测接口（如 models 列表 / 余额查询），或在明确提示"会产生费用"后再执行。

### 6.4 【代码事实】`manufacturer` 为 null 时 `switch` 抛 NPE

`TextAiProviderFactory.create` 只校验了 `apiKey`，随后直接 `switch (config.getManufacturer())`。Java 对 `String` 的 `switch` 遇 `null` 会抛 `NullPointerException`（不是走 default）——**不会**落到 `OpenAiCompatibleProvider`。配置漏填 `manufacturer` 时报的是 NPE 而非友好错误。建议先判空再分派。

### 6.5 【代码事实】`delete(id)` 非事务，可能留下孤儿映射

```java
public void delete(Long id) {
    if (configMapper.selectById(id) == null) throw new BizException(ErrorCode.NOT_FOUND);
    configMapper.deleteById(id);                                   // ① 删配置
    aiModelMapMapper.delete(new LambdaQueryWrapper<AiModelMap>().eq(AiModelMap::getConfigId, id)); // ② 删映射
}
```
方法**没有 `@Transactional`**。若 ① 成功、② 失败，则 `t_ai_model_map` 残留指向已删除 config 的记录 → 运行时报「模型配置不存在」。建议加 `@Transactional`。

### 6.6 【代码事实】密钥以静态变量承载，多密钥/多租户不可行

`AesUtil.aesKey` 是 `static`。这意味着整个 JVM 只能有一把主密钥。若未来要做「每租户独立密钥」，当前设计不支持。

### 6.7 【代码事实】热路径每次查库 + 解密 + new 实例

`getTextProvider` 每次调用都会：查 `t_ai_model_map`、查 `t_config`、AES 解密、`new` 一个 Provider。在 Agent 工具循环（每次 LLM 调用都取一次 Provider）中会放大开销。带配置缓存（如 Caffeine + 失效通知）可显著降低。

### 6.8 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 改了 AES key 密文行为不变 | `setKey` 未调用（§6.1） | 启动时注入密钥 |
| 相同 key 密文相同 | 固定 IV（§6.2） | 随机 IV / AES-GCM |
| 点"测试连通"就产生费用 | 真发起生成（§6.3） | 换轻量探测 |
| 报 NPE 而非"未配置厂商" | manufacturer 为 null（§6.4） | 判空 |
| 报"模型配置不存在" | 孤儿映射（§6.5） | `delete` 加事务 |
| 报"未配置功能映射: xxx" | `t_ai_model_map` 缺该 key | 在管理端补映射 |
| 列表看不到完整 key | 掩码（预期） | 正常行为 |

## 7. 可迁移落地方案

`【落地建议】`

1. **两层路由是好模式**：`功能标识 → 模型配置`，业务只认功能名；换模型零改代码。
2. **新厂商默认走兼容协议**：只让"协议不兼容"的厂商写分支，降低接入成本。
3. **主密钥必须来自配置**：启动时显式 `setKey`，并对密钥长度做校验；绝不在源码里写死。
4. **加密用随机 IV + 认证加密（AES-GCM）**，密文自包含 IV。
5. **出参只回掩码**，且 require 二次输入才能改 key；列表接口不返回明文。
6. **配置热更新 + 缓存**：解析结果可缓存，管理端保存时失效缓存。
7. **连通性测试要"零副作用"**：优先用只读探测；若必须真实调用，需显式二次确认。
8. **配置变更要原子**（`@Transactional`），删除要保证不留孤儿。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 功能映射 + 工厂（本方案） | 多厂商、业务与模型解耦 | 单厂商（过度设计） |
| 依赖注入多个 Bean + `@Qualifier` | 厂商固定、编译期确定 | 需运行时可配 |
| 规则引擎（Drools 等） | 复杂路由条件 | 简单多对一关系 |
| 网关层路由（如 LiteLLM） | 复用、多语言 | 引入一跳 |
| 配置中心（Nacos/Apollo） | 多环境统一管理 | 增加依赖 |

## 9. 验收清单

- [ ] 业务只传 `functionKey` 即可拿到 Provider。
- [ ] 未配映射/配置时返回明确业务错误。
- [ ] `t_config.api_key` 落库为密文，列表只回掩码。
- [ ] **启动时从配置注入 AES 主密钥**（不再硬编码）。
- [ ] 加密使用随机 IV（相同明文密文不同）。
- [ ] `manufacturer` 为空有友好兜底而非 NPE。
- [ ] 删除配置与其映射在同一事务。
- [ ] `updateModelMaps` 全量替换原子生效。
- [ ] 连通性测试无副作用（或明确提示费用）。
