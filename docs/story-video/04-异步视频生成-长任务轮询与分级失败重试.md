# 04 异步视频生成：长任务轮询与分级失败重试

> 标签：异步任务 / 轮询 / 重试策略 / 版本管理 / 首尾帧连续性
> ⭐ 本系列中**迁移价值最高**的一篇：AI 生成类长任务几乎都会遇到同样的模式。

---

## 1. 场景与边界

视频生成是**典型的「提交任务 + 异步回调/轮询」模型**：一次生成动辄数十秒到数分钟，远超 HTTP 超时。

平台需要：
- 用户点击生成后**立即返回**，不阻塞请求；
- 后台轮询任务状态，成功后落库视频 URL；
- 失败时**分级重试**：不是简单重跑，而是「先优化提示词，再降分辨率」；
- 同一镜头支持**多版本**，可切换/重生成；
- 同一剧本相邻镜头用**上一镜的尾帧作为下一镜首帧**，保证画面连续。

边界：本场景讲 `VideoService` 的任务编排与重试；底层厂商差异见第 02 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 长任务不能同步等 | 必须 `@Async` 后台 + 轮询 |
| 失败原因多样 | 提示词违规、分辨率过高、厂商限流…… 需差异化重试 |
| 重试不能无限 | 需 `retryCount` / `maxRetry` 上限 |
| 生成结果要可追溯 | 每次重生成/重试产生版本，用户可回退 |
| 镜头间连续性 | 需要跨记录取「上一镜尾帧」 |
| 轮询占线程 | 需控制轮询间隔与超时，避免线程池耗尽 |

## 3. 实现链路

### 3.1 主流程

```
submitGenerate(projectId, scriptId, shotId, ...)
  → 配额校验 quotaService.checkAndConsume(userId, "video", 1)
  → 新建 Video: retryCount=0, maxRetry=3, version=1, resolution=默认1080p
  → 首帧 = 上一镜 lastFrame（若有）
  → generateVideoAsync(...)   [@Async，立即返回]

generateVideoAsync(videoId, prompt, imagePath, resolution)
  → getVideoProvider(functionKey).createTask(request) → taskId
  → while(true): pollTask(taskId)
        completed → 落库 videoUrl + lastFrameUrl，结束
        失败/异常 → 进入分级重试
```

### 3.2 分级重试（关键设计）

| 重试次数 | 策略 | 依据 |
| --- | --- | --- |
| 第 1 次失败 | 原参数重试 | — |
| `nextRetry == 2` | **润色提示词**（调 `videoPromptPolish` 文本模型） | `VideoService.java:154-157` |
| `nextRetry == 3` | **降分辨率**（4K→1080p→720p→480p） | `VideoService.java:158-161` |

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| `@Async` + `while` 轮询 | 实现简单，无需厂商回调地址 | 占用线程；应用重启后任务丢失 |
| 固定 2s 轮询 | 简单 | 高频任务对厂商 API 压力大，可改指数退避 |
| 分级重试（润色/降分辨率） | 比盲目重跑命中率高 | 依赖文本模型可用性；逻辑分支多 |
| 版本号递增 | 结果可追溯、可回退 | 存储成本增加 |
| 首尾帧接力 | 提升分镜连续性 | 强依赖厂商返回 `lastFrameUrl`，缺失则退回静态图 |

## 5. 关键工程实现

**（1）首尾帧连续性（`VideoService.java:75-80`）**
```java
String firstFrame = imagePath;
Video prev = /* 同 scriptId 前一条视频 */;
if (prev != null && prev.getLastFrame() != null) {
    firstFrame = prev.getLastFrame();
}
```
`【工程推断】` 只有当厂商确实返回 `lastFrameUrl` 时接力才成立（`VolcengineVideoProvider` 的 `VideoTaskResult.lastFrameUrl`）。

**（2）分级重试（`VideoService.java:144-164`）**：失败后 `nextRetry` 递增，第二次「润色提示词」，第三次「降分辨率」，超过 `maxRetry` 则停止。【代码事实】

**（3）轮询（`VideoService.java:130-134`）**：`pollTask` 未完成则 `Thread.sleep(2000)` 继续。

## 6. 踩坑根因排障

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 接口请求超时 | 误把生成放主线程 | 确认走 `@Async generateVideoAsync` |
| 任务一直 pending | 轮询在应用重启后中断 | 需持久化 `taskId` 并支持启动后恢复（当前未见） |
| 重试次数不生效 | `retryCount` 未持久化或未回读 | 检查 `VideoService.java:144-148` |
| 降分辨率没触发 | `nextRetry` 计算与 `maxRetry` 关系 | 确认 `maxRetry=3` 且分支命中 |
| 相邻镜头仍不连续 | 厂商未返回 `lastFrameUrl`，或未按 `scriptId` 排序 | 检查 `prev` 查询排序与 `lastFrame` 是否为空 |
| 版本混乱 | `selectVersion` 未回写「当前版本」标记 | 检查版本选择落库逻辑 |
| 线程池被打满 | 并发任务多 + 2s 轮询 | 增大线程池或改调度轮询（参考第 06 篇 `ScheduledExecutorService`） |

## 7. 可迁移落地方案

`【落地建议】` 一套可复用的「AI 长任务」编排模板：

1. **提交即返回**：入口只做校验 + 建记录（状态 `pending`）+ 触发异步，返回 `taskId`。
2. **统一任务状态机**：`pending → processing → completed / failed`，落库。
3. **异步执行 + 轮询**：`@Async` 提交厂商任务，独立线程轮询；轮询间隔用**指数退避**并设**总超时**。
4. **分级重试**：不同失败阶段用不同策略（优化输入 → 降规格 → 换厂商），而非简单重跑。
5. **版本化结果**：每次重生成 `version+1`，支持切换与回退。
6. **可恢复**：持久化厂商 `taskId`，应用重启后扫描未完成任务继续轮询（本项目尚未实现，建议补齐）。
7. **限流/配额前置**：提交前扣配额（见第 11 篇）。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| `@Async` + 轮询（本方案） | 无回调能力、单体应用 | 需要重启恢复的大规模任务 |
| 厂商 Webhook 回调 | 厂商支持回调 | 无公网回调地址 |
| 独立调度/工作流引擎（XXL-Job、Temporal、Celery） | 任务量大、需持久化与重试编排 | 小规模 |
| 消息队列 + 消费者 | 削峰、解耦（本项目 compose 有 RocketMQ 但代码未接） | 无 MQ 基建 |

## 9. 验收清单

- [ ] `submitGenerate` 返回后主线程不阻塞。
- [ ] 轮询成功落库 `videoUrl`。
- [ ] 第 2 次失败触发提示词润色；第 3 次触发降分辨率。
- [ ] 超过 `maxRetry` 后停止并记录失败原因。
- [ ] 同 `scriptId` 相邻镜头首帧取自上镜尾帧（有尾帧时）。
- [ ] 重生成产生新版本且旧版本可查。
- [ ] 配额不足时提交被拒并给出明确错误。
