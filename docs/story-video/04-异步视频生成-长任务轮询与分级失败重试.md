# 04 异步视频生成：长任务轮询与分级失败重试

> 标签：异步长任务 / 状态轮询 / 分级重试 / 首尾帧衔接
>
> 证据根：`story-video-service/src/main/java/io/binghe/framework/service/VideoService.java`

---

## 1. 场景与边界

文生视频是典型的**长任务**：一次生成动辄几十秒到十几分钟，各家厂商 API 都是「提交任务 → 拿 taskId → 轮询查询 → 拿结果 URL」的两段式。平台要解决：

1. **提交即返回**：HTTP 接口不能等十几分钟，必须异步；
2. **轮询与超时**：后台轮询到完成/失败，且要有超时兜底；
3. **失败分级重试**：同样是失败，直接重放往往还失败，需要「换策略」；
4. **镜头连续性**：相邻镜头的画面要连贯（用上一镜的尾帧做下一镜的首帧）；
5. **多版本与选择**：一条分镜可生成多个版本，需标记选中版本。

边界：
- 本文聚焦单条视频任务的「提交—轮询—失败处理—接力」闭环。
- 视频厂商的 Provider 抽象、任务状态映射见 `AbstractVideoProvider` / `VolcengineVideoProvider`。
- 多个镜头如何被流水线批量驱动见第 06 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 异步执行载体 | `@Async` 是首选，但**自调用会绕过代理**（本项目实际踩中，见 §3.3/§6.1） |
| 轮询成本 | 轮询间隔太密打爆厂商，太疏延长总时长 |
| 超时语义 | 轮询超时是「失败」还是「继续等」需明确 |
| 重试要「换招」 | 原样重放无意义，需引入 prompt 润色、分辨率降级 |
| 重试次数落库 | 重试过程要可观测、可人工干预（`retryCount`/`maxRetry`） |
| 首尾帧接力 | 需要「上一个已完成且被选中」的镜头，排序/选中逻辑易错 |
| 线程池保护 | 线程池满时如何处理提交（拒绝策略） |

## 3. 实现链路

### 3.1 提交与异步执行

```
submitGenerate(projectId, scriptId, shotId, configId, prompt, imagePath)
  ├─ [配额] SecurityUtil.getCurrentUserId() → quotaService.checkAndConsume(userId,"video",1)
  ├─ 建 Video 记录：state=0(生成中) / retryCount=0 / maxRetry=3 / version=1 / selected=1
  ├─ 解析厂商与分辨率（configId → VideoConfig，缺省 "1080p"）
  ├─ 首尾帧接力：imagePath==null 时 findPrevCompleted(scriptId, shotId).lastFrame
  ├─ insert
  └─ generateVideoAsync(videoId, prompt, firstFrame, resolution)   ← @Async
```

### 3.2 轮询与失败分级

- 轮询：`maxPolls = 500`，每次 `Thread.sleep(2000)` → **最长约 1000s（≈16.6 分钟）**，超时返回 `failed/轮询超时`。
- 成功：写 `filePath`、`lastFrame`、`state=1`、`duration`。
- 失败：`handleFailure` 按 `nextRetry` 分级：

| nextRetry | 策略 |
| --- | --- |
| 1 | 原样重试 |
| 2 | 调文本模型**润色 prompt** 后重试（`videoPromptPolish`） |
| 3 | **降分辨率**后重试（4K/2160p→1080p→720p→480p） |
| >maxRetry | `state=-1` 终态失败 |

### 3.3 关键结构（截图式）

```java
videoMapper.insert(video);
generateVideoAsync(video.getId(), prompt, firstFrame, video.getResolution()); // ← 同类内直接调用
...
@Async

```
【代码事实】`VideoService.java:81-87`。**这是同一 Bean 内的自调用**，Spring 的 `@Async` 依赖代理，自调用不会走代理 → 该方法很可能**同步执行在调用线程上**（见 §6.1）。

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| `@Async` + 自定义 `ThreadPoolTaskExecutor` | 简单、Spring 原生 | **自调用失效**；平台线程池非虚拟线程 |
| 轮询而非 Webhook | 厂商普遍支持轮询，实现统一 | 拉高延迟与无效请求；16.6 分钟上限 |
| 失败分级（润色→降级） | 比盲目重放命中率高 | 引入文本模型调用，增加成本与依赖 |
| 首尾帧接力 | 提升镜头连贯性 | 依赖上一镜成功且被选中，串行依赖 |
| 多版本 + selected 标记 | 支持人工挑片 | 查询与排序复杂，易错 |
| 拒绝策略仅告警 | 不阻塞提交线程 | **任务静默丢失**（见 §6.3） |

## 5. 关键工程实现

**（1）分级重试核心（`VideoService.java:139-166`）**

```java
private void handleFailure(Video video, String errorMessage) {
    video.setErrorMessage(errorMessage);
    int nextRetry = (video.getRetryCount() != null ? video.getRetryCount() : 0) + 1;
    int maxRetry = video.getMaxRetry() != null ? video.getMaxRetry() : 3;
    if (nextRetry <= maxRetry) {
        video.setRetryCount(nextRetry);
        videoMapper.updateById(video);
        String retryPrompt = video.getPrompt();
        String retryResolution = video.getResolution();
        if (nextRetry == 2)      retryPrompt = polishPrompt(video.getPrompt());     // 换提示词
        else if (nextRetry == 3) retryResolution = downgradeResolution(video.getResolution()); // 降分辨率
        generateVideoAsync(video.getId(), retryPrompt, null, retryResolution);      // ← 自调用
    } else {
        video.setState(-1);
        videoMapper.updateById(video);
    }
}
```

**（2）首尾帧接力（`VideoService.java:194-214`）**

```java
List<Video> completed = videoMapper.selectList(new LambdaQueryWrapper<Video>()
        .eq(Video::getScriptId, scriptId)
        .eq(Video::getState, 1)
        .eq(Video::getSelected, 1)
        .isNotNull(Video::getLastFrame)
        .orderByAsc(Video::getShotId));
Video prev = null;
for (Video v : completed) {
    if (v.getShotId() != null && v.getShotId().compareTo(currentShotId) < 0) prev = v;
}
return prev;
```

**（3）轮询超时兜底（`VideoService.java:124-137`）**：固定 500 次 × 2s，超时与中断都归一为 `failed`。

**（4）线程池配置（`AsyncConfig.java:24-35`）**：core 4 / max 16 / queue 100，拒绝策略只打日志。

## 6. 踩坑根因排障

### 6.1 【代码事实 + 工程推断】`@Async` 被自调用绕过 → 长任务可能阻塞调用线程

`submitGenerate`（第 82 行）与 `handleFailure`（第 161 行）都在**同一个 Bean 内部**直接调用 `generateVideoAsync`。Spring `@Async` 基于代理拦截，自调用不经过代理，注解**不生效**：

- 【工程推断】`submitGenerate` 会在调用它的线程（很可能是 HTTP 请求线程或流水线线程）里**同步**跑完 `createTask` + 最长 16.6 分钟轮询，HTTP 请求直接超时；第 06 篇的流水线也会因此阻塞。
- 与之对照，第 06 篇 `startPipeline → executePipelineAsync` 也是同样的自调用模式。

**修复方向**：把异步方法抽到独立 Bean（如 `VideoTaskRunner`）注入调用；或自注入代理 `@Lazy VideoService self`；或用 `AopContext.currentProxy()`（需 `exposeProxy=true`）；或直接用 `CompletableFuture.runAsync` 明确异步。

### 6.2 【代码事实】shotId 用字符串字典序比较/排序，两位数会错位

`orderByAsc(Video::getShotId)` 与 `shotId.compareTo(currentShotId)` 都是**字符串**比较。当 shotId 为 `"1".."10"` 时字典序为 `1,10,11,2,3...`：

- 镜头 2 想找「前一个」时，`"10".compareTo("2") < 0` 为真，可能把**第 10 镜的尾帧**当作第 2 镜的首帧，**画面时序错乱**。
- 正确做法：`shotId` 用数值列/序号列排序，或在应用层按数值解析后比较。

### 6.3 【代码事实】线程池拒绝策略会「静默丢任务」

```java
executor.setRejectedExecutionHandler((r, e) -> log.warn("Async task rejected, thread pool is full"));
```
当 core 4 / queue 100 / max 16 被打满时，新任务**直接丢弃且不抛异常**。对视频场景意味着：`generateVideoAsync` 被拒后 Video 记录永远停在 `state=0`，前端一直转圈，`countPending` 永远大于 0 → 流水线卡在 Step 10 直到超时。

**建议**：改用 `CallerRunsPolicy`（背压）或将拒绝的 videoId 记入重试队列。

### 6.4 【代码事实/工程推断】`@Async` 未使用虚拟线程

`application.yml` 中若开启 `spring.threads.virtual.enabled=true`，Spring Boot 会提供虚拟线程执行器；但本仓显式定义了名为 `taskExecutor` 的**平台线程池**，`@Async` 默认会优先使用它 → 虚拟线程配置失去意义。长阻塞轮询（`Thread.sleep`）尤其适合虚拟线程，此处未受益。

### 6.5 【代码事实】超时被当作失败、且会走分级重试

轮询超时返回 `state="failed"` → 进入 `handleFailure`。也就是说「厂商其实还在生成、只是我们等累了」也会被当成失败并重新提交，**可能产生重复任务与重复计费**。

### 6.6 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 提交接口长时间不返回 | `@Async` 自调用被绕过（§6.1） | 抽独立 Bean / 自注入 |
| 任务一直 `state=0` | 线程池拒绝静默丢弃（§6.3） | 看 `Async task rejected` 日志；换拒绝策略 |
| 相邻镜头画面跳变 | shotId 字符串排序（§6.2） | 改数值排序 |
| 重复计费/重复任务 | 轮询超时被判失败后重提（§6.5） | 超时改用「继续等待/人工确认」 |
| 重试始终失败 | 3 次都用同样 prompt/分辨率且都超时 | 观察 `retryCount` 与 `errorMessage` |
| `retryVideo` 报「已达最大重试次数」 | `retryCount >= maxRetry` | 重置 `retryCount` 或提高 `maxRetry` |

## 7. 可迁移落地方案

`【落地建议】`

1. **异步执行一定验证代理是否生效**：把 `@Async`/`@Transactional` 方法放到**独立 Bean**，或显式自注入/`AopContext`；不要在同 Bean 内自调用后假设它异步。
2. **长任务建模为「任务表 + 状态机」**：`state`（生成中/成功/失败）、`retryCount`、`maxRetry`、`taskId`、`errorMessage`、`version`、`selected` 全部落库，便于重试、对账、人工干预。
3. **失败重试要「变更量」**：每次重试改变一个变量（提示词/分辨率/模型/时长），并记录策略，避免无效重放。
4. **首尾帧接力用可靠的排序键**：用数值型 `shotIndex`，不要用可变的 `shotId` 字符串。
5. **超时与失败分开处理**：超时应进入「待确认/继续轮询」而非直接判失败，防止重复提交与重复计费。
6. **线程池拒绝要有兜底**：`CallerRunsPolicy` 做背压，或把被拒任务写入补偿队列；绝不要静默 `log.warn` 了事。
7. **善用虚拟线程**：IO 密集 + 大量 `sleep` 的轮询场景，虚拟线程收益明显；注意别被自定义平台线程池覆盖。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| `@Async` + 轮询（本方案） | 中小规模、单实例、厂商只提供轮询 | 高并发、多实例、要求精确计费 |
| 消息队列 + 消费端轮询 | 多实例、可削峰、可重试 | 引入 MQ 运维成本 |
| 调度中心（XXL-Job/Quartz） | 已有调度平台、需要可视化 | 与业务状态机耦合较重 |
| 厂商 Webhook 回调 | 厂商支持时最省资源 | 需公网回调、签名校验 |
| 工作流引擎（Temporal） | 长事务、跨服务编排 | 较重 |

## 9. 验收清单

- [ ] `submitGenerate` 立即返回，生成在独立线程执行（验证线程名非请求线程）。
- [ ] 轮询到完成写回 `filePath`/`lastFrame`/`state=1`/`duration`。
- [ ] 失败按 1→2→3 分级（原样/润色/降分辨率），超过 `maxRetry` 置 `state=-1`。
- [ ] `shotId` 排序正确（两位数不串位）。
- [ ] 相邻镜头首帧 = 上一镜尾帧。
- [ ] 线程池打满时任务不丢（拒绝策略可验证）。
- [ ] 轮询超时行为明确，不重复提交/重复计费。
- [ ] `countPending` 在全部结束后归零。
