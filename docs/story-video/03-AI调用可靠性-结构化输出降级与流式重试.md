# 03 AI 调用可靠性：结构化输出降级与流式重试

> 标签：LLM 工程化 / 结构化输出 / 降级 / 重试 / SSE

---

## 1. 场景与边界

Agent 与业务层大量依赖 **结构化 JSON 输出**（如分镜、资产、章节计划）。但不同厂商/模型对结构化输出的支持差异很大：

- 有的支持原生 `json_schema`（严格模式）；
- 有的只支持 `json_object`（保证是 JSON，但不保证 schema）；
- 有的完全不支持，只能把 schema 写进提示词。

若不做兼容，换一个模型就会大面积解析失败。此外网络抖动需要重试，**流式（SSE）与同步**的重试方式也不同。

边界：本场景讲**请求体的结构化输出兼容策略**与**重试模板**；Provider 路由见第 02 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 能力差异无法用一套请求体覆盖 | 需按「模型能力表」决定是否下发 `response_format` |
| 不支持 schema 时如何兜底 | 把 JSON Schema 追加到 system prompt |
| 同步与流式重试语义不同 | 同步可 `Thread.sleep` 阻塞重试；流式需 Reactor `retryWhen` |
| 只应重试可恢复错误 | 4xx 参数错误不该重试，超时/5xx/网络错误应重试 |
| SSE 手写解析要健壮 | 需处理畸形行、`[DONE]`、usage 等 |

---

## 3. 实现链路

### 3.1 结构化输出三级降级（`buildRequestBody`）

```
if (responseFormat == "json_schema" && jsonSchema != null) {
    if (capability.responseFormat == "schema")   → 下发原生 response_format=json_schema(strict)
    else if (capability.responseFormat == "object") → 下发 response_format=json_object + 把 schema 追加到 prompt
    else                                          → 只把 schema 追加到 prompt
}
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 模型能力内置表 | 避免每次调用试探，直接决定请求体形态 | 新模型需手动登记；能力表与真实能力可能漂移 |
| 三级降级 | 同一套业务代码兼容所有模型 | 「不支持 schema」时解析成功率依赖模型遵循提示词能力 |
| prompt 注入 schema | 最后兜底，保证请求总能发出 | 增加 token 消耗，且非强保证 |
| 同步用固定退避、流式用 Reactor | 各用各的阻塞模型，简单直接 | 同步阻塞占用线程 |
| tool 能力门控 | 无 tool 能力的模型不下发 tools，避免报错 | 无工具时需业务侧降级 |

## 5. 关键工程实现

**（1）结构化输出降级（`AbstractOpenAiCompatibleProvider.java:113-139`）**：核心是 **先看能力、再决定下发方式**，保证任何模型都能收到「期望 JSON」的信号。【代码事实】

**（2）工具调用解析容错（`AbstractOpenAiCompatibleProvider.java:340-358`）**：`tool_calls` 解析失败时降级为只取 `content`，不让整个响应失败。【代码事实】

**（3）重试策略分离（`AiRetryTemplate.java`）**
```java
// 同步：最多 MAX_RETRIES 次，退避 2s/4s/8s
for (int attempt = 0; attempt <= MAX_RETRIES; attempt++) {
    try { return action.get(); }
    catch (Exception e) {
        if (attempt < MAX_RETRIES && isRetryable(e)) { Thread.sleep(BACKOFF_MS[attempt]); continue; }
        else if (!isRetryable(e)) break;
    }
}
// 流式：Reactor 退避
action.get().retryWhen(Retry.backoff(MAX_RETRIES, Duration.ofSeconds(2)).maxBackoff(Duration.ofSeconds(8)).filter(this::isRetryable));
```
`【工程推断】` `MAX_RETRIES` 由 `BACKOFF_MS` 长度推断为 3。

## 6. 踩坑根因排障

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 换模型后 JSON 解析全失败 | 模型不在能力表，落到 `DEFAULT=object` 甚至无 JSON 支持 | 在 `TextModelRegistry` 登记正确 `responseFormat` |
| 本可用原生 schema 却走了 prompt 注入 | `responseFormat` 登记错误 | 对照 `register(...)` 参数 |
| 无 tool 能力模型报 `tools` 参数错误 | 能力表 `tool=false` 时已不下发；若仍报错说明登记为 `true` | 修正能力表 |
| 流式内容缺失/乱码 | SSE 行解析对畸形行、多 `data:` 处理不足 | 查 `doStreamPost` 逐行逻辑 `:258-299` |
| 参数错误被反复重试 | `isRetryable` 把 4xx 判为可重试 | 收敛 `isRetryable`，只放行超时/5xx/网络异常 |
| 同步重试拖慢接口 | `Thread.sleep` 阻塞业务线程 | 长退避场景改异步或限制重试次数 |

## 7. 可迁移落地方案

`【落地建议】`

1. **能力表驱动请求体**：为每个模型维护 `{responseFormat, supportsImage, supportsThinking, supportsTool}`，请求构造前查询。
2. **三级结构化输出降级**：`json_schema` → `json_object + prompt schema` → `prompt schema`，保证「总能发出去」。
3. **解析容错**：任何字段解析失败都要有降级路径（如丢弃 tool_calls 保留 content），避免整响应失败。
4. **重试分级**：可重试异常（超时/5xx/连接重置）才重试；参数类错误立即失败；同步用固定退避，流式用反应式退避。
5. **SSE 手写解析要防御**：逐行读、跳过畸形行、识别 `[DONE]`、兼容 `data:` 前缀。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 自研能力表 + 工厂 | 多厂商、需精细控制 | 单一厂商 |
| 用官方 SDK（各厂商） | 稳定、省心 | 依赖膨胀、统一封装难 |
| 统一网关（如 LiteLLM） | 想屏蔽厂商差异 | 额外运维组件 |
| Spring Retry / Resilience4j | 需要熔断/限流等更复杂策略 | 简单退避场景过重 |

## 9. 验收清单

- [ ] 同一业务代码在「支持 schema / 只支持 object / 不支持 JSON」三类模型上都能拿到可解析结果。
- [ ] 能力表未登记的模型走 `DEFAULT` 且不抛异常。
- [ ] 参数错误不触发重试；超时/5xx 触发且退避为 2/4/8s。
- [ ] 流式接口能处理畸形 SSE 行而不中断。
- [ ] `tool_calls` 解析失败时降级为 content，不整体失败。
- [ ] 重试日志包含次数、操作名、等待时长。
