# 03 AI 调用可靠性：结构化输出降级与流式重试

> 标签：大模型接入 / 结构化输出 / 重试与退避 / 降级
>
> 证据根：`story-video-ai/src/main/java/io/binghe/framework/ai/**`

---

## 1. 场景与边界

平台要同时对接 9 家文本大模型（OpenAI / Anthropic / Gemini / Qwen / 智谱 / 豆包 / DeepSeek / Xai / 通用 OpenAI 兼容），而这些模型对「结构化 JSON 输出」的支持能力差异极大：

- 有的支持原生 `response_format: {type: json_schema}`（严格喂 schema）；
- 有的只支持 `response_format: {type: json_object}`（保证是 JSON，但不保证字段）；
- 有的完全不支持，只能把 schema 写进提示词里「求」模型输出 JSON。

工程问题：**同一份业务代码（只声明「我要一个符合某 schema 的 JSON」），如何在一个统一基类里，按目标模型的能力自动选择降级策略？** 以及调用失败后，**哪些错误该重试、各用哪种退避、流式与同步是否共用一套重试**。

边界：
- 本文只讲文本 Provider 的「请求构造 → 结构化输出 → 重试」横切能力。
- 厂商路由与密钥解密见第 02 篇；视频/图片的异步轮询重试见第 04 篇。
- 本文涉及的重试缺陷（见 §6）是**代码事实**，但「是否真的不重试」属运行期行为，列入 §10 待确认。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 能力差异建模 | 无法用「厂商名」判断，必须精确到**模型名**级别的能力表 |
| 降级要无损 | schema 从原生通道降级到提示词后，仍需引导模型输出可解析 JSON |
| 响应可能被包裹 | 模型常把 JSON 放进 ```json 代码块或前后加说明，需提取 |
| 重试要甄别错误 | 429/5xx/网络超时可重试；4xx（参数错、鉴权错、配额）重试无意义 |
| 同步与流式不同 | 同步可 `Thread.sleep` 退避；流式基于 Reactor，需用 `Flux.defer + retryWhen` 惰性重建 |
| 退避要可控 | 固定 3 次、指数退避（2s/4s/8s），避免放大对上游的压力 |

## 3. 实现链路

### 3.1 能力表：把「模型名」映射到「输出能力」

`TextModelRegistry` 用 `ModelCapability` 记录每个模型的三项能力：`responseFormat`（`schema`/`object`/`none`）、是否支持图片输入、是否支持思考、是否支持工具调用；未登记模型落到默认值 `("object", false, false, false)`。

```
ModelCapability{responseFormat, image, think, tool}
DEFAULT = ("object", false, false, false)   // 未登记模型：退化为 json_object + 提示词
registry.getCapability(model)                // 按精确模型名查表，缺省回落 DEFAULT
```

### 3.2 三级结构化输出降级（核心）

`AbstractOpenAiCompatibleProvider.buildRequestBody` 是整套降级的落点：

| 能力 | 请求体处理 | 说明 |
| --- | --- | --- |
| `schema` | 发 `response_format.json_schema`（`strict=true` + `schema`） | 原生严格结构化 |
| `object` | 发 `response_format.json_object` + **把 schema 追加进 system 提示词** | 半可靠，做双保险 |
| `none` | 只把 schema 追加进 system 提示词 | 完全靠提示词约束 |

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 统一走 OpenAI 兼容协议 + 薄适配 | 9 家厂商里大多数提供 OpenAI 兼容端点，一个基类覆盖 | 非兼容厂商需各自子类覆写 |
| 能力**按模型名**精确登记 | 同厂商不同模型能力不同（如是否支持 json_schema） | 能力表需持续维护 |
| 三级降级而非「一刀切走提示词」 | 能原生约束时优先原生，减少解析失败 | 代码分支变多 |
| schema 同时写进提示词（object/none 级） | 双保险，模型更可能给对字段 | 略增 token |
| 同步重试用 `Thread.sleep`、流式用 Reactor `retryWhen` | 各自贴合其执行模型 | 两套重试逻辑，行为不完全一致（见 §6） |
| `Flux.defer(action)` 包裹流式调用 | 每次重试都重新建立请求（否则复用同一 Flux 无意义） | — |

## 5. 关键工程实现

**（1）三级降级：一次 `if/else` 完成能力分派**

```java
if ("json_schema".equals(request.getResponseFormat()) && request.getJsonSchema() != null) {
    if ("schema".equals(capability.getResponseFormat())) {
        // 原生：response_format.json_schema (strict)
        responseFormat.put("type", "json_schema");
        jsonSchema.put("name", "response");
        jsonSchema.put("strict", true);
        jsonSchema.set("schema", objectMapper.readTree(request.getJsonSchema()));
        responseFormat.set("json_schema", jsonSchema);
        body.set("response_format", responseFormat);
    } else if ("object".equals(capability.getResponseFormat())) {
        // 半原生：json_object + schema 进提示词
        responseFormat.put("type", "json_object");
        body.set("response_format", responseFormat);
        systemPrompt = appendSchemaToPrompt(systemPrompt, request.getJsonSchema());
    } else {
        // 纯提示词
        systemPrompt = appendSchemaToPrompt(systemPrompt, request.getJsonSchema());
    }
}
```
【代码事实】`AbstractOpenAiCompatibleProvider.java:113-139`

**（2）同步重试：固定 3 次 + 指数退避，失败后统一包装成 `AI_CALL_FAILED`**

```java
private static final int MAX_RETRIES = 3;
private static final long[] BACKOFF_MS = {2000, 4000, 8000};

for (int attempt = 0; attempt <= MAX_RETRIES; attempt++) {
    try { return action.get(); }
    catch (Exception e) {
        lastException = e;
        if (attempt < MAX_RETRIES && isRetryable(e)) { Thread.sleep(BACKOFF_MS[attempt]); }
        else if (!isRetryable(e)) { break; }          // 不可重试：立即失败
    }
}
throw new BizException(ErrorCode.AI_CALL_FAILED, operationName + " failed after retries: ...");
```
【代码事实】`AiRetryTemplate.java:28-54`

**（3）流式重试：`Flux.defer` 保证每次重试重建请求**

```java
public Flux<String> executeStream(Supplier<Flux<String>> action, String operationName) {
    return Flux.defer(action)
            .retryWhen(Retry.backoff(MAX_RETRIES, Duration.ofSeconds(2))
                    .maxBackoff(Duration.ofSeconds(8))
                    .filter(this::isRetryable)
                    .onRetryExhaustedThrow((spec, signal) ->
                            new BizException(ErrorCode.AI_CALL_FAILED, ...)));
}
```
【代码事实】`AiRetryTemplate.java:56-65`

## 6. 踩坑根因排障

### 6.1 【代码事实】网络错误/超时实际上不会被重试（高优先级）

`isRetryable` 判定「业务码 500（含）到 510（不含）可重试」：

```java
if (e instanceof BizException biz && biz.getCode() >= 500 && biz.getCode() < 510) return true;
```
而 `AI_CALL_FAILED = 510`。可 `doPost` 恰恰把 **网络异常和未知异常都包装成 510**：

```java
catch (IOException e) { throw new BizException(ErrorCode.AI_CALL_FAILED, "Network error: ..."); }  // =510
```

**后果**：文本 Provider 上的网络错误、连接超时、以及所有 4xx（含 400 参数错、401 鉴权错、404）都被压成 510，而 510 落不进 `[500,510)` 区间 → `isRetryable` 返回 false → **`execute` 立刻 `break` 并抛错，一次都不重试**。第 68 行 `e instanceof IOException` 那个分支在文本 Provider 路径上基本是**死代码**。

**根因**：错误码空间设计冲突——`510` 既表示「不可重试的调用失败」，又被用作「网络错误」的统一编码。

**排查**：遇到「AI 偶发失败、日志里完全没有 `AI call retry x/3` 行」时，先看失败异常的 code 是不是 510。

**修复方向**：把网络类异常用独立码（如 `511 AI_TIMEOUT` 或新增 `NETWORK_ERROR`）表达，并让 `isRetryable` 显式包含它；或让 `doPost` 在 IOException 时抛**原始 IOException**（`execute` 的 `isRetryable` 已识别 `IOException`）。

### 6.2 【代码事实】5xx 中 ≥510 的状态码也不会被重试

`doPost` 对 `code >= 500` 一律抛 `BizException(code)`。若上游返回 520/522/529 等（部分网关/云厂商会），这些码落不进 `[500,510)` → 不重试。只有 500–509 才重试。

### 6.3 【代码事实】流式重试对 HTTP 级错误基本失效

`doStreamPost` 无论哪种失败，都把 HTTP 错误统一包成 `AI_CALL_FAILED(510)`：

```java
sink.error(new BizException(ErrorCode.AI_CALL_FAILED, "Stream HTTP " + response.code() + ": " + errBody));
```
而 `executeStream` 的重试过滤器是 `filter(this::isRetryable)` → 510 不可重试。**只有**最外层 `catch (Exception e) { sink.error(e); }`（第 299 行）漏出的原始异常（如 IOException）才可能被重试。

### 6.4 【代码事实】429 语义冲突：配额用尽会触发无意义重试

`ErrorCode.QUOTA_EXCEEDED = 429`，与「HTTP 429 限流」同码。`isRetryable` 把 429 视为可重试：

```java
if (e instanceof BizException biz && biz.getCode() == 429) return true;
```
于是**用户配额用完**（QuotaService 抛 429）如果发生在被 `AiRetryTemplate` 包裹的调用链里，会被重试 3 次、累计等待 14s 后仍失败，徒增延迟与日志噪音。建议配额用非 429 的独立码。

### 6.5 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 结构化输出字段缺失/解析失败 | 模型只支持 `object` 或 `none`，schema 未真正约束 | 查 `TextModelRegistry` 该模型能力；必要时升级模型或改用提示词强约束 |
| 响应前带 ```json 导致反序列化失败 | 未走 `extractJson` 或用错重载 | 用 `invoke(req, Class)`；确认 `extractJson` 生效 |
| 偶发失败从不重试 | 错误被压成 510（§6.1） | 看异常 code；修 `isRetryable` 或异常包装 |
| 流式断了不重连 | 流式 HTTP 错误 → 510（§6.3） | 见 §6.3 |
| 配额耗尽拖 14s 才报错 | 429 被当限流重试（§6.4） | 拆分错误码 |
| 一直提示 `response_format` 不支持 | 模型名未登记，落到 DEFAULT 的 `object` | 在 `TextModelRegistry` 登记该模型能力 |

## 7. 可迁移落地方案

`【落地建议】`

1. **能力表按「模型名」而非「厂商名」登记**，并设计一个安全的 DEFAULT（不支持就用提示词兜底），让新模型接入「不登记也能跑」。
2. **结构化输出做三级降级**：原生 schema → json_object + 提示词 → 纯提示词，且**降级时始终把 schema 塞进提示词**做双保险。
3. **重试前必须能区分「可重试/不可重试」**：把网络错误、超时、限流、5xx 定义为可重试，参数/鉴权/配额定义为不可重试；**不要在错误码空间上复用同一个码表达相反语义**。
4. **同步与流式分别实现重试**：流式一定要用 `Flux.defer(...)`/`defer` 包裹，确保重试是「重建请求」而非「重订阅同一实例」。
5. **退避用指数 + 上限**（本仓 2s/4s/8s，共 3 次），避免雪崩式重试。
6. **失败统一包装**：对外暴露一个业务错误码（如 `AI_CALL_FAILED`），把最后一次真实 cause 带在 message 里，便于定位。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 统一 OpenAI 兼容基类 + 能力表（本方案） | 大量厂商走兼容协议 | 协议差异大的厂商（需各自子类） |
| 每厂商独立 SDK（官方 SDK） | 追求厂商全能力 | 维护成本高、抽象难统一 |
| JSON 修复库（如 `json-repair`）兜底 | 模型输出偶发脏 JSON | 不能替代 schema 约束 |
| 网关层统一重试（如 LiteLLM / 自研网关） | 多语言、多服务复用 | 引入额外一跳与运维成本 |
| 强约束模型 + 原生 schema only | 只对接少数强模型 | 无法覆盖弱能力模型 |

## 9. 验收清单

- [ ] 对 `schema` 能力模型，请求体含 `response_format.json_schema` 且 `strict=true`。
- [ ] 对 `object` 能力模型，请求体含 `json_object` 且 system 提示词含 schema。
- [ ] 对 `none` 能力模型，schema 出现在 system 提示词。
- [ ] `invoke(req, Class)` 能解析 ```json 包裹的响应。
- [ ] 同步调用遇可重试错误时，日志出现 `AI call retry x/3` 且退避 2s/4s/8s。
- [ ] 网络错误/超时**能**被重试（对照 §6.1 修复后验证）。
- [ ] 流式断连后能重建请求重试。
- [ ] 配额用尽**不**触发无意义重试。
- [ ] 未登记模型能走 DEFAULT 正常出结果。
