# 10 语音合成：对白抽取与角色音色匹配

> 标签：TTS / 对白解析 / 音色匹配 / 配置治理
>
> 证据根：`story-video-service/src/main/java/io/binghe/framework/service/{TtsService,TtsConfigService}.java`

---

## 1. 场景与边界

剧本是文本，要变成带配音的成片，必须：**从剧本里抽出「谁说什么」→ 给每个角色匹配音色（音色/语速/音调/情感）→ 逐条合成音频 → 存储并记录**。

工程问题：

1. **对白抽取**：剧本格式不固定（`角色：台词`、`【旁白】…` 混排），如何稳定解析？旁白怎么识别？
2. **音色匹配**：角色名（文本）如何映射到 `t_tts_config`（按 characterId）？匹配不到怎么办？
3. **逐条容错**：一条合成失败不能中断整集；
4. **存储**：音频文件与记录如何组织；
5. **厂商差异**：不同 TTS 厂商参数不同，如何统一。

边界：
- 本文聚焦「抽取 + 匹配 + 合成 + 落库」。
- TTS 阶段的流水线位置见第 06 篇（Step 9，默认关闭）。
- 音频文件存储见第 08 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 剧本格式不一 | 中英文冒号、全角方括号、旁白标记都要兼容 |
| 角色名 vs characterId | 剧本里是名字，配置里是 id，需要经 `t_assets` 中转 |
| 匹配不到 | 要有默认音色兜底 |
| 逐条失败 | 单条失败要跳过但可观测 |
| 参数默认值 | voiceId/speed/pitch/emotion 都缺省时的行为要明确 |
| 厂商选择 | 全局 functionKey 与「每角色 manufacturer」可能冲突 |
| 记录状态 | 成功的记录才应是 state=1 |

## 3. 实现链路

### 3.1 抽取（`extractDialogues`）

对剧本按行处理：

```
逐行 trim，空行跳过
├─ 若 raw 以「【」开头且含「】」：
│     取 [] 内为 tag；text = [] 之后内容
│     narration = ("旁白".equals(tag))
│     text 非空则加入结果
├─ 否则用 DLG = ^(.+?)[:：](.+)$ 匹配：
│     group(1)=角色名，group(2)=台词，narration=false
│     text 非空则加入结果
└─ 都不匹配 → 丢弃该行（舞台说明/描述会被忽略）
```

### 3.2 音色匹配（`matchVoices`）

```
查询 t_assets where projectId=? and type='role'          → 角色资产
查询 t_tts_config where projectId=?                       → 项目音色配置
├─ 配置按 characterId 建索引；characterId == null 的作为 defaultConfig
├─ 角色资产按 name 建索引
└─ 对每条对白：
     ├─ 已匹配过同名角色则复用
     ├─ 旁白 → defaultConfig
     ├─ 精确匹配：name → asset → characterId → config
     ├─ 模糊匹配：asset.name 与 name 互相 contains → config
     └─ 都没 → defaultConfig
```

### 3.3 合成与落库（`generate`）

```
Script = selectById(scriptId)；空 → warn 返回
dialogues = extractDialogues(script.content)；空 → info 返回
voiceMap  = matchVoices(projectId, dialogues)
provider  = aiProviderService.getTtsProvider("tts")     ← 全局 functionKey
for dl in dialogues:
    try:
        config = voiceMap.get(dl.characterName)
        voiceId  = config.voiceId 或 "default"
        speed    = config.speed   或 1.0
        pitch    = config.pitch   或 1.0
        emotion  = config.emotion 或 "neutral"
        audio = provider.synthesize(TtsRequest{text,voiceId,speed,pitch,emotion,format=mp3})
        audio 空 → warn 跳过
        key = "tts/" + projectId + "/" + UUID + ".mp3"
        url = ossService.upload(key, audio, "audio/mpeg")
        insert TtsAudio{projectId,scriptId,text,characterName,voiceId,filePath=url,state=1}
    catch: log.error（不中断后续）
```

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| 正则抽取对白 | 无依赖、快 | 格式敏感，舞台说明/多行对白丢失 |
| 「角色名→资产→characterId→配置」链 | 复用资产表，配置可挂到角色 | 多一跳查询，依赖资产 name 唯一 |
| 精确 + 模糊 + 默认三级 | 尽量匹配上 | 模糊匹配不稳定（见 §6.3） |
| 逐条 try/catch | 单条失败不影响整集 | 失败静默，整体成功率不可见 |
| 用全局 functionKey `"tts"` 拿 Provider | 与其它能力一致的抽象 | **每角色 manufacturer 被忽略**（见 §6.2） |
| 音频落 OSS + 记录落库 | 统一存储 | 依赖第 08 篇的 OSS 可用性 |

## 5. 关键工程实现

**（1）对白抽取（`TtsService.java:54-81`）**

```java
for (String raw : scriptContent.split("\n")) {
    raw = raw.trim();
    if (raw.isEmpty()) continue;
    DialogueLine dl = new DialogueLine();
    if (raw.startsWith("【") && raw.contains("】")) {          // 【旁白】xxx
        int end = raw.indexOf('】');
        String tag = raw.substring(1, end).trim();
        dl.setCharacterName(tag);
        dl.setText(raw.substring(end + 1).trim());
        dl.setNarration("旁白".equals(tag));
        if (!dl.getText().isEmpty()) lines.add(dl);
        continue;
    }
    Matcher m = DLG.matcher(raw);                              // 角色：台词
    if (m.matches()) {
        dl.setCharacterName(m.group(1).trim());
        dl.setText(m.group(2).trim());
        dl.setNarration(false);
        if (!dl.getText().isEmpty()) lines.add(dl);
    }
}
```

**（2）三级匹配（`TtsService.java:116-145`）**

```java
Assets role = roleByName.get(name);
if (role != null && configByCharId.containsKey(role.getId())) {   // 精确
    result.put(name, configByCharId.get(role.getId())); continue;
}
TtsConfig fuzzy = null;
for (Map.Entry<String, Assets> entry : roleByName.entrySet()) {   // 模糊
    if (entry.getKey().contains(name) || name.contains(entry.getKey())) {
        Assets matched = entry.getValue();
        if (configByCharId.containsKey(matched.getId())) { fuzzy = configByCharId.get(matched.getId()); break; }
    }
}
result.put(name, fuzzy != null ? fuzzy : defaultConfig);
```

**（3）逐条合成 + 落库（`TtsService.java:168-204`）**

## 6. 踩坑根因排障

### 6.1 【代码事实】`getVoices` 硬编码，与实际支持的厂商不符

```java
voices.add(Map.of("id","zh-CN-XiaoxiaoNeural","name","晓晓（女）","manufacturer","azure"));
... 只有 azure 与 openai ...
```
但 TTS Provider 工厂实际支持 `FishAudio / Volcengine / Azure / Aliyun` 四家。结果是**前端音色下拉里选不到 volcengine/aliyun/fishaudio 的音色**，而这些厂商的 `voiceId` 语义与 azure/openai 完全不同。建议改为向厂商拉取真实音色列表（或维护配置表）。

### 6.2 【代码事实】每角色 `manufacturer` 被忽略，「谁的声音」由全局路由决定

`TtsConfig` 有 `manufacturer` 字段（`TtsConfig.java:42`），`TtsConfigService.update` 也允许改它。但合成时：

```java
TtsAiProvider provider = aiProviderService.getTtsProvider("tts");   // 全局 functionKey
```
Provider 由**全局的 `tts` 映射**决定，`TtsRequest` 里也不含 `manufacturer`。因此「A 角色用火山、B 角色用 Azure」这种需求**无法实现**——所有角色都走同一个厂商。要支持需让 `TtsRequest`/Provider 解析感知每角色的 manufacturer。

### 6.3 【代码事实】模糊匹配遍历 `HashMap`，结果不确定

```java
for (Map.Entry<String, Assets> entry : roleByName.entrySet()) { ... break; }
```
`roleByName` 是 `HashMap`，迭代顺序不保证。当多个角色名互相 `contains`（如「林」「林晚」「林晚儿」）时，**同一份数据可能匹配到不同音色**。应改为「最长匹配优先」等确定性规则。

### 6.4 【代码事实】`state` 字段存在但匹配时不生效

`TtsConfig.state`（1=启用/0=禁用）从未在 `matchVoices` 里被判断。**禁用的音色配置照样会被使用**。查询应加 `.eq(TtsConfig::getState, 1)`。

### 6.5 【代码事实】旁白只会取「最后一条」characterId 为 null 的配置

```java
for (TtsConfig c : configs) {
    if (c.getCharacterId() == null) defaultConfig = c;   // 循环覆盖
    else configByCharId.put(c.getCharacterId(), c);
}
```
若存在多条 `characterId=null` 的配置，`defaultConfig` 是**迭代到的最后一条**，结果不确定；且它同时充当「旁白音色」和「兜底音色」两种语义，容易互相干扰。

### 6.6 【代码事实】正则会把「冒号在中间的非对白行」误判为对白

`DLG = ^(.+?)[:：](.+)$` 匹配「任意非空 + 冒号 + 任意非空」。例如：

- 舞台说明「场景：咖啡馆的清晨」→ 被当成角色「场景」说的话；
- 含 URL 的行「来源：http://abc」→ 角色「来源」。

另外**多行对白**（同一角色连续多行）不会被合并，会被拆成多条（第二条没有冒号则被丢弃）。建议：维护一份「已知角色名集合」，只把角色名命中的行当作对白；或用更严格的剧本标记。

### 6.7 【代码事实】逐条失败静默，整体成功率不可观测

单条 `catch` 只 `log.error`，既不落失败记录、也不统计。最后只打一行 `Generated N audio records`（N 是**尝试数**而非成功数）。整集配音少了哪几句，前端无从得知。建议：失败也落库（`state=0` + `errorMessage`），或返回成功/失败计数。

### 6.8 【代码事实】TTS 不消耗配额

`QuotaService` 只覆盖 `chapter`/`image`/`video`（见第 11 篇），**TTS 没有配额检查**。若 TTS 按字符/时长计费，会成为成本黑洞。

### 6.9 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 选不到某厂商音色 | `getVoices` 硬编码（§6.1） | 扩充/动态拉取 |
| 改了角色厂商没变化 | manufacturer 被忽略（§6.2） | 让 Provider 感知 manufacturer |
| 音色匹配时对时错 | 模糊匹配顺序不定（§6.3） | 确定性匹配规则 |
| 禁用的音色仍被用 | 未过滤 state（§6.4） | 查询加 state=1 |
| 旁白音色有时变 | defaultConfig 覆盖（§6.5） | 约束唯一或显式选择 |
| 旁白/说明被当台词 | 正则太宽（§6.6） | 已知角色名白名单 |
| 配音有缺失但无提示 | 静默跳过（§6.7） | 失败落库 + 统计 |
| TTS 成本失控 | 无配额（§6.8） | 增加 tts 配额 |

## 7. 可迁移落地方案

`【落地建议】`

1. **剧本对白要有结构化格式**：与其用宽松正则，不如约定明确标记（如 `@角色{...}` 或 JSON 脚本），从源头保证可解析。
2. **匹配要确定性**：精确 > 最长前缀/后缀 > 默认；禁止遍历无序集合「命中即止」。
3. **配置要有生效状态**：所有查询默认只取 `state=1`；停用配置必须真正停用。
4. **每角色可指定厂商/音色**：把厂商信息纳入请求模型，而不是全局路由。
5. **失败也要落库**：`state=0 + errorMessage`，让前端能显示「哪句没合成」；统计成功/失败数。
6. **配额/成本覆盖所有 AI 能力**：文本、图片、视频、TTS 都应纳入配额与用量统计。
7. **音色列表动态化**：从厂商 API 或配置表读取，避免硬编码与实现脱节。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 正则抽取 + 配置匹配（本方案） | 剧本格式较规整 | 自由格式、多行对白 |
| LLM 抽取对白（结构化输出） | 格式混乱、需理解语义 | 成本/延迟高 |
| 剧本 JSON 化 | 从生成阶段就产出结构 | 需改上游剧本生成 |
| 厂商一站式配音 | 省事 | 灵活性差 |
| 声纹克隆/自定义音色 | 追求角色辨识度 | 需训练、成本高 |
