# 01 认证：多入口登录鉴权与令牌单会话失效

> 标签：认证 / JWT / Redis 单会话 / 多入口（HTTP + WebSocket）
>
> 证据根：`story-video-security/.../security/**` + `story-video-config/.../SecurityConfig.java` + `story-video-service/.../AuthService.java`

---

## 1. 场景与边界

系统有**两条入口**需要认证，且必须共用同一套身份：

1. **HTTP REST**（`/api/**`）：绝大多数业务接口；
2. **WebSocket/STOMP**（`/ws/**`）：Agent 实时对话与事件推送。

工程问题：

1. **无状态**：REST 用 JWT，不依赖 Session；
2. **主动失效**：用户登出、被禁用、或在别处重新登录后，**旧 token 必须立刻失效**——纯 JWT 做不到，需引入外部存储；
3. **多入口统一**：WebSocket 也要能校验同一 token，并识别「是谁、哪个项目」；
4. **鉴权主体传递**：业务层如何拿到当前用户/角色。

边界：
- 本文聚焦「登录 → 签发 → 校验 → 失效 → 多入口复用」。
- WebSocket 的握手细节与会话隔离见第 07 篇。
- 配额与登录用户的关系见第 11 篇。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| 主动失效 vs 无状态 | JWT 自带过期，但要支持「登出即失效」必须有服务端状态 |
| 每请求校验 | 引入 Redis 校验后，认证路径与 Redis 强耦合 |
| 多入口复用 | WebSocket 握手要能拿到并验证同一个 token |
| 主体类型 | 业务层要能直接拿到 `userId` 与 `role` |
| 角色模型 | 单角色还是多角色？权限粒度到哪？ |
| 密钥健壮性 | HMAC 密钥过短会导致启动失败 |

## 3. 实现链路

### 3.1 登录与签发

```
POST /api/auth/login {name, password}
  └─ AuthService.login
       ├─ select t_user by name；不存在 → UNAUTHORIZED
       ├─ passwordEncoder.matches(raw, user.password) 不一致 → UNAUTHORIZED
       ├─ user.status == 0 → FORBIDDEN
       ├─ select t_user_role；role 缺省 "viewer"
       ├─ jwtTokenProvider.generateToken(userId, name, role)
       │    ├─ JWT：subject=userId，claim name/role，expiration
       │    └─ Redis：SET video:token:{userId} = token  TTL=expiration   ← 单会话
       └─ 返回 LoginResponse{token, userId, name, role}
```

### 3.2 请求校验（HTTP）

```
任意请求 → JwtAuthenticationFilter.doFilterInternal
  ├─ extractToken：Authorization: Bearer <token>
  ├─ token != null && tokenProvider.validateToken(token)
  │    ├─ parseToken（验签 + 过期）
  │    ├─ userId = subject
  │    └─ Redis GET video:token:{userId} == token ？  ← 单会话核心
  ├─ 通过 → 构造 Authentication(principal=userId, authority=ROLE_<ROLE大写>) 放入 SecurityContext
  └─ filterChain 继续
```

### 3.3 失效

```
POST /api/auth/logout（需已认证）
  └─ authService.logout(SecurityUtil.getCurrentUserId())
       └─ jwtTokenProvider.invalidateToken(userId) → DEL video:token:{userId}
```

- **登出**：删除 Redis 键 → 该 token 即使签名/未过期，`validateToken` 也返回 false。
- **重新登录**：`generateToken` 覆盖 Redis 键 → 旧 token 自动作废（**单会话**）。
- **被禁用**：仅 `login` 时检查 `status==0`；已签发的 token 在有效期内**仍可用**（见 §6.5）。

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| JWT + Redis 单会话 | 无状态 + 可主动失效 | 每请求一次 Redis 往返；强依赖 Redis |
| Redis 键按 userId | 天然单会话（同用户只保留最新 token） | **同账号不能多端同时在线** |
| 登出即删键 | 语义清晰 | Redis 不可用时无法登出 |
| Token 走 `Authorization: Bearer` | 标准 | WebSocket 需另想办法（走 query） |
| BCrypt 存密码 | 抗暴力破解 | 需正确配置强度 |
| STATELESS 会话 | 无服务端 session | 无法用 session 相关特性 |
| 单角色（`t_user_role` 一条） | 简单 | 多角色/细粒度权限受限 |

## 5. 关键工程实现

**（1）签发 + 写 Redis（`JwtTokenProvider.java:38-55`）**

```java
public String generateToken(Long userId, String name, String role) {
    Date now = new Date();
    Date expiryDate = new Date(now.getTime() + expiration);
    String token = Jwts.builder()
            .subject(String.valueOf(userId))
            .claim("name", name).claim("role", role)
            .issuedAt(now).expiration(expiryDate)
            .signWith(key).compact();
    // 写 Redis，支持主动失效
    redisTemplate.opsForValue().set(REDIS_TOKEN_PREFIX + userId, token, expiration, TimeUnit.MILLISECONDS);
    return token;
}
```

**（2）校验：验签 + Redis 比对（`JwtTokenProvider.java:67-77`）**

```java
public boolean validateToken(String token) {
    try {
        Claims claims = parseToken(token);
        Long userId = Long.parseLong(claims.getSubject());
        String cached = redisTemplate.opsForValue().get(REDIS_TOKEN_PREFIX + userId);
        return token.equals(cached);          // 必须与 Redis 中的当前 token 一致
    } catch (Exception e) {
        return false;
    }
}
```

**（3）过滤器放主体（`JwtAuthenticationFilter.java:37-44`）**

```java
if (StringUtils.hasText(token) && tokenProvider.validateToken(token)) {
    Long userId = tokenProvider.getUserIdFromToken(token);
    String role = tokenProvider.getRoleFromToken(token);
    var auth = new UsernamePasswordAuthenticationToken(
            userId, null, List.of(new SimpleGrantedAuthority("ROLE_" + role.toUpperCase())));
    SecurityContextHolder.getContext().setAuthentication(auth);
}
```

**（4）Security 规则（`SecurityConfig.java:31-41`）**

```java
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/login", "/api/auth/captcha").permitAll()
        .requestMatchers("/ws/**").permitAll()
        .anyRequest().authenticated())
    .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
```

**（5）建用户三写（`UserService.java:82-106`）**：`@Transactional` 内插 `t_user` + `t_user_role(viewer)` + `t_user_quota(50/200/100)`。

## 6. 踩坑根因排障

### 6.1 【代码事实】Redis 是认证路径的强依赖，故障即"全员掉线"

`validateToken` 每次都要读 Redis。若 Redis 不可用，`redisTemplate.get` 抛异常 → 被 `catch (Exception)` 吞掉 → **返回 false** → 所有请求 401。即 **Redis 宕机 = 全站无法登录/访问**（fail-closed）。这是取舍：安全上更保守，可用性上更脆弱。若希望降级，可保留"Redis 不可用时退化为纯 JWT 校验 + 明确降级告警"。

### 6.2 【代码事实】`role.toUpperCase()` 对空 role 会 NPE

```java
String role = tokenProvider.getRoleFromToken(token);
new SimpleGrantedAuthority("ROLE_" + role.toUpperCase())
```
`getRoleFromToken` 返回 claim 值；若 token 无 `role` claim（例如由旧版本或其它系统签发但同密钥），`role` 为 null → **NPE**（发生在过滤器里，返回 500 而非 401）。建议判空兜底为 `viewer`。

### 6.3 【代码事实】`/api/auth/captcha` 是"幽灵路径"

`SecurityConfig` 放行了 `/api/auth/captcha`，但全仓**没有任何 captcha 控制器/实现**（`AuthController` 只有 login/logout）。同时 `AuthService.login` **完全不校验验证码**。结果是：

- 放行配置形同虚设；
- **登录无验证码、无失败次数限制、无锁定** → 可被暴力破解/撞库。

建议：要么补验证码与限流（如失败 N 次锁定、IP 限流），要么删除误导性配置。

### 6.4 【代码事实】无角色/权限分级，任何登录用户可访问全部 `/api/**`

`SecurityConfig` 只有 `anyRequest().authenticated()`，**没有基于 authority 的授权规则**。`SecurityUtil.getCurrentRole()` 虽能拿到角色，但没有任何 `hasRole("admin")` 之类的限制。若系统存在"用户管理"等管理员接口（`UserService.listUsers/createUser/deleteUser`），**普通 viewer 也能调用**。建议对管理类接口加 `hasRole('admin')`。

### 6.5 【代码事实】禁用用户后，已签发 token 在有效期内仍可用

禁用只在 `login` 时检查：

```java
if (user.getStatus() != null && user.getStatus() == 0) throw new BizException(ErrorCode.FORBIDDEN);
```
`validateToken` 不查用户状态。用户被禁用后，只要其 token 未过期（默认 **24 小时**）且仍在 Redis 中，就仍能访问。要即时生效，需在禁用时 `invalidateToken(userId)`，或在校验时附带查询状态。

### 6.6 【代码事实】同账号无法多端同时在线

Redis 键是 `video:token:{userId}`，**新登录覆盖旧 token**。这是"单会话"的设计后果：用户在 A 设备登录后，B 设备登录会让 A 掉线。若产品需要多端，需改为「按 deviceId 存多个 token」。

### 6.7 【代码事实】JWT 密钥过短会导致启动失败

`Keys.hmacShaKeyFor(secret.getBytes())` 要求密钥 **≥ 256 bit（32 字节）**，否则抛 `WeakKeyException`。默认值 `video-default-jwt-secret-key-change-in-production-2026` 足够长，但若生产把 `JWT_SECRET` 设成短字符串（如 `abc123`），**应用直接启动失败**。建议在启动时对长度做校验并给出清晰错误。

### 6.8 【代码事实】默认密钥若不改，等于无鉴权

`application.yml` 里 `video.jwt.secret` 默认值明文写在仓库中。若生产未设置 `JWT_SECRET` 环境变量，任何人可用该默认密钥伪造 token（且还需绕过 Redis 校验——但结合 §6.1 的 Redis 比对，伪造 token 仍需匹配 Redis，攻击面受限）。仍强烈建议强制外部注入。

### 6.9 常见现象对照表

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| Redis 一挂全部 401 | 强依赖（§6.1） | 评估降级策略 |
| 校验 token 报 500 | role 为 null NPE（§6.2） | 兜底 viewer |
| 登录接口无验证码可刷 | 幽灵 captcha（§6.3） | 补验证码 + 限流 |
| 普通用户能进管理接口 | 无授权规则（§6.4） | 加 hasRole |
| 禁用后仍能操作 | 不校验状态（§6.5） | 禁用时失效 token |
| 换个设备登录就掉线 | 单会话（§6.6） | 按设备存 token |
| 启动报 WeakKeyException | 密钥过短（§6.7） | 强制 ≥32 字节 |
| 登出后 token 仍有效 | 未连 Redis / 多实例键不一致 | 检查 Redis 与登出链路 |

## 7. 可迁移落地方案

`【落地建议】`

1. **"JWT + 服务端当前 token 快照"是支持主动失效的常用组合**：JWT 负责自包含与签名，Redis 负责"是否仍被认可"。键 `auth:token:{userId}`，登出/改密/禁用时删除。
2. **认证路径要明确故障策略**：Redis 不可用时，选择 fail-closed（全 401）还是 fail-open（仅验签），并配监控告警。
3. **区分"认证"与"授权"**：`authenticated()` 只是认证；管理接口必须再加 `hasRole`/`hasAuthority`。
4. **敏感状态变更要联动失效**：禁用用户、改密码、改角色时，主动 `invalidateToken`。
5. **登录要防爆破**：验证码 + 失败计数 + 账号/IP 限流 + 锁定策略。
6. **多端支持要提前设计**：键按 `userId + deviceId`，或引入 refresh token 机制。
7. **密钥规范化**：启动时校验长度/格式；生产强制外部注入；支持密钥轮换。
8. **统一多入口认证**：WebSocket 握手复用同一个 `validateToken`，并额外校验资源归属（见第 07 篇）。

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| JWT + Redis 单会话（本方案） | 需主动失效的中小型系统 | 高吞吐（每请求 Redis）、多端 |
| 纯无状态 JWT | 简单、无需主动失效 | 需要登出/禁用立即生效 |
| Session + Redis | 传统、易理解 | 需处理跨域/移动端 |
| OAuth2/OIDC + 授权服务器 | 多应用 SSO、第三方登录 | 引入较重 |
| Refresh + Access 双 token | 长会话、多端、安全性好 | 实现复杂 |
| API Gateway 统一鉴权 | 微服务、统一入口 | 单体场景收益低 |

## 9. 验收清单

- [ ] 正确账号密码能拿到 token 并访问受保护接口。
- [ ] 错误密码/不存在用户返回 401，禁用用户返回 403。
- [ ] 无 token / 伪造 token / 过期 token 均被拒。
- [ ] **登出后原 token 立即失效**。
- [ ] 同账号再次登录后，旧 token 失效。
- [ ] 禁用用户时其 token 立即失效（若产品要求）。
- [ ] WebSocket 握手复用同一 token 校验。
- [ ] 管理接口有角色/权限限制。
- [ ] Redis 故障时行为符合预期并有告警。
- [ ] JWT 密钥来自外部且长度合法。
