# 01 认证：多入口登录鉴权与令牌单会话失效

> 标签：认证 / JWT / Redis / WebSocket
> 结论来源：`【代码事实】` 可定位源码；`【工程推断】` 合理推断；`【落地建议】` 可迁移做法。

---

## 1. 场景与边界

平台同时提供两类入口，都需要同一份登录态：

- **HTTP 接口**：`/api/**` 绝大多数接口需要登录。
- **WebSocket 长连接**：`/ws/agent/{type}/{projectId}`、`/ws/pipeline/{projectId}`，Agent 实时事件推送。

要求：**登录一次、两处通用**；**登出后令牌立即失效（单会话）**，而不是等到 JWT 自然过期。【代码事实】`JwtTokenProvider` 把最新 token 写入 Redis（`video:token:{userId}`），校验时不仅验签还要与 Redis 中的值比对。

边界（本场景不涉及）：
- 不涉及第三方 OAuth / SSO；
- 不涉及多设备并发会话（当前设计是「每个用户同时只有一个有效令牌」）。

---

## 2. 约束与难点

| 难点 | 说明 |
| --- | --- |
| JWT 天然无状态，登出难 | 纯 JWT 无法主动失效，必须引入服务端状态 |
| 无状态与可失效的矛盾 | 用 Redis 保存「当前有效 token」，兼顾签名校验与主动失效 |
| 两个入口要共用同一套校验 | HTTP 用 Filter，WebSocket 用握手拦截器，两者都要能拿 `userId` |
| WebSocket 无法带自定义 Header | 浏览器 `WebSocket` 不能自定义 `Authorization` 头，只能走 query 参数 |
| 路径参数要在握手期一次性解析 | Agent 类型、projectId 需在握手时写入 session 属性供后续事件使用 |

---

## 3. 实现链路

### 3.1 HTTP 登录 → 访问

1. `POST /api/auth/login` → `AuthService.login`：查用户 → BCrypt 校验密码 → 校验状态 → 生成 JWT 并回写 Redis → 返回 token。【代码事实】
2. 后续请求带 `Authorization: Bearer <token>` → `JwtAuthenticationFilter` 提取 token → `JwtTokenProvider.getUserIdFromToken` → 写入 `SecurityContextHolder`。【代码事实】
3. `SecurityConfig` 放行登录接口与 `/ws/**`，其余需认证。【代码事实】

### 3.2 WebSocket 握手 → 事件

1. 客户端连接 `/ws/agent/novel/{projectId}?token=xxx`。
2. `JwtHandshakeInterceptor.beforeHandshake` 取 query 参数 `token`，`validateToken` 通过后写入 `userId`，并解析路径得到 `agentType`/`projectId`。【代码事实】
3. 连接建立后发布 `SessionConnectedEvent` → `WebSocketEventListener` 据 session 属性创建 Agent。【代码事实】

## 4. 关键选型与权衡

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| JWT + Redis 双校验 | 保留 JWT 无状态传递，同时获得主动失效能力 | 每次请求多一次 Redis 读；Redis 故障将导致全校验失败 |
| 单 token 覆盖写 | 天然实现「新登录挤掉旧登录」的单会话 | 不支持多端并发；覆盖写可被用于「抢登」 |
| WS 走 query 参数 token | 浏览器 WebSocket API 不支持自定义头 | token 会进 URL/日志，需注意脱敏 |
| 过滤器用 `OncePerRequestFilter` | 保证每请求只执行一次 | — |

## 5. 关键工程实现

**（1）令牌生成即登记（`JwtTokenProvider.java:42-54`）**
```java
String token = Jwts.builder()
    .subject(String.valueOf(userId))
    .claim("name", name).claim("role", role)
    .issuedAt(now).expiration(expiryDate)
    .signWith(key).compact();
redisTemplate.opsForValue().set(REDIS_TOKEN_PREFIX + userId, token, expiration, TimeUnit.MILLISECONDS);
```

**（2）校验即比对（`JwtTokenProvider.java:67-77`）**：先 `parseToken` 验签（失败返回 `false`），再从 Redis 取当前 token 比对，二者一致才算有效。这样「登出后 token 即使未过期也失效」。【代码事实】

**（3）两入口共用（`WebSocketConfig.java:62-77`）**：握手拦截器复用 `jwtTokenProvider.validateToken/getUserIdFromToken`，与 HTTP 过滤器同一套逻辑。【代码事实】

## 6. 踩坑根因排障

| 现象 | 根因 | 排查/处理 |
| --- | --- | --- |
| 登出后旧 token 仍可用 | `validateToken` 未做 Redis 比对，或 `invalidateToken` 未调用 | 确认 `JwtTokenProvider.java:72-73` 的比对逻辑与登出接口调用 |
| 接口 401 但 token 未过期 | Redis 中 token 被新登录覆盖（单会话特性） | 属预期；如需多端需改存储结构（如 `token:{userId}:{device}`） |
| WebSocket 连接被拒 | 未带 `token` query 参数，或参数名不是 `token` | 对照 `WebSocketConfig.java:63` |
| 重启后全部掉线 | Redis 中 token 丢失/被清 | 检查 Redis 持久化与 `video:token:*` 键 |
| `/api/auth/captcha` 404 | `SecurityConfig.java:36` 放行了验证码接口，但**该接口不存在** | 移除放行项或补接口 |

## 7. 可迁移落地方案

`【落地建议】` 可直接复用的最小认证套件：

1. **JWT 只负责签名与携带身份**，服务端用 Redis 存 `当前有效 token`，键 `token:{userId}`，TTL 与 JWT 过期一致。
2. **校验函数三件事**：验签 → 取主体 → 与 Redis 比对；异常一律 `false`。
3. **登出 = 删 Redis 键**；改密/封号同理。
4. **HTTP 用 Filter、WS 用握手拦截器**，二者调用同一个 `TokenProvider`，避免两套逻辑漂移。
5. **WS token 建议用一次性 ticket 换取**，避免长期 token 出现在 URL。

---

## 8. 替代方案与适用边界

| 方案 | 适用 | 不适用 |
| --- | --- | --- |
| 纯 JWT（无服务端状态） | 无登出/封号需求、纯内部服务 | 需要主动失效 |
| Redis 黑名单（存被吊销 token） | token 数量可控、允许自然过期 | 高频登出、黑名单膨胀 |
| Redis 白名单（本方案：存当前有效 token） | 需要单会话、强失效 | 多端并发会话 |
| 网关统一鉴权（如 Spring Cloud Gateway） | 微服务多入口 | 单体应用（本平台） |

## 9. 验收清单

- [ ] 登录成功返回 token，Redis 存在 `video:token:{userId}`。
- [ ] 登出后旧 token 立即 401。
- [ ] 新登录后旧 token 立即 401（单会话）。
- [ ] WS 带 `token` 可连、不带/错误 token 被拒。
- [ ] WS 握手成功后 session 属性含 `userId`/`agentType`/`projectId`。
- [ ] JWT 过期时间与 `video.jwt.expiration` 一致（默认 86400000ms）。
- [ ] Redis 不可用时给出明确错误而非静默放行。
