# 08 可恢复运行时：让 Agent 在崩溃后接着跑

> 01–07 讲的是"正常路径"。这一篇讲**失败路径**：进程被杀、网络断、工具执行到一半、Provider 流中断之后，Pi 如何保证"已完成的副作用不重放、未完成的能续上"。
> 主要源码/文档：`packages/agent/src/harness/`、`packages/agent/docs/harness.md`（规范）、`assistant-durability.md`、`tool-durability.md`、`values.md`、`runtime-simplification.md`。
> 行号与规范基于 0.87.0（storage format 4 WIP，尚未稳定）。

## 8.1 要解决的问题：不确定的外部副作用

一个普通 Agent 循环，最难的从来不是"调模型"，而是：**模型请求、工具执行、hook 都有外部副作用，而且它们可能在中途崩溃**。

- 发出去一次 Provider 请求，被计费了，但进程在收到响应前死了——这次请求到底算不算？
- `bash` 删了文件，还没把结果写回会话就崩溃——重跑会删两次吗？
- 一个 hook 写了一条外部审计记录，崩溃后重放会写第二条吗？

【设计取舍】Pi 的答案是：**不追求 exactly-once 的外部副作用**（§0.6 明确列为 non-goal），而是用"**意图 + 结算**两个提交"把不确定性**显式地持久化**，让恢复时能根据策略决定"重放 / 跳过 / 合成中断结果"。这是整篇的核心思想。

## 8.2 三层存储与一条铁律

【代码事实】`harness.md §0.3` 规定：所有持久化数据只能是三种形态之一，**没有第三个地方**。

```
entries       会话树       —— write-once，只追加
values/lists  当前可变状态 —— value 可替换；list 只可整表删除
usage ledger  成本历史     —— 只追加
```

> 铁律：*Every payload is in an entry, a bound value/list, or the ledger.*

三个推论：

1. **原子事务**（§1.4）：一次 `commit(writes[])` 里，entry/usage 插入与 value/list 写入**要么全成功，要么全失败**，序列号严格递增。不存在"事务执行到一半"的崩溃态。
2. **恢复不靠日志回放**：`operationState(operationId)` 在每次持久化转移后都被**完整整体替换**（不是增量）。崩溃后读到哪个状态，就从对应过程继续，**不重放日志、不靠"缺什么"来推断**。
3. **写入即事实**：会话树一旦写入永不修改/删除；成本行只追加。

【给新项目】很多人第一反应是"用 WAL / event-sourcing 存操作日志，恢复时重放"。Pi 明确反其道而行：**把状态存成"当前值的完整快照"，而不是操作历史**。理由是恢复逻辑必须是"从某个点直接分派"，而不是"重演一遍可能带副作用的操作"。这大幅降低了恢复代码的复杂度和二次副作用风险。

## 8.3 四个基本名词

| 名词 | 形态 | 关键性质 |
|------|------|---------|
| `Entry` | 会话树节点 | `id/parentId/seq/timestamp/type` + payload；写一次永不改 |
| `Value<T>` | 绑定地址上的可变值 | 只能整体替换；`value<T>(namespace, key)` 构造，地址一次绑定 |
| `ValueList<T>` | 只追加列表 | 元素不可变，仅支持整 key 删除 |
| `UsageRow` | 成本账本行 | 每次结算的 Provider 尝试写一行，永不删除，计费独立于编排状态 |

【代码事实】地址是**绑定命名空间**：`pi` 与 `pi.*` 保留给内建。内建清单（§1.3）里比较关键的几个：

- `pi.branch.tip`：某 lane 下次追加的位置
- `pi.op.meta` / `pi.op.state`：操作的接受信息 / 完整断点
- `pi.pending.entry`：尚未落到树上的完整内容
- `pi.pending.tool_output`：工具**有界**进度检查点（只在 effect 不确定期间存在）
- `pi.pending.assistant_frame`：流式 assistant 帧前缀（只在响应 effect pending 期间存在）
- `pi.result`：终态只读记录，写一次、恢复时**不读**

【设计取舍】`namespace` 采用字符串 + 保留前缀约定，而**不做运行时权限检查**（构造器不校验 `pi.*` 归属）。文档明确说：应用误用保留命名空间属于"trusted-programming defect"，靠构造器测试而非运行时特权来约束。这是有意的性能/复杂度取舍。

## 8.4 操作状态机：一个可恢复的"断点"

【代码事实】`OperationState` 是一个 **13 叶子的扁平联合类型**（§3.2）：

```
starting · checkpoint · assistant.ready · assistant.effect_pending ·
assistant.retry_wait · tools · deferred.suspended · deferred.effect_pending ·
summary.deciding · summary.ready · summary.effect_pending · summary.retry_wait ·
navigation.ready_to_commit
```

配套的状态图（§3.5）用 mermaid 描述正常路径。**取消（cancel）是正交的**：在每次普通分派前检查 `control`，若是 `cancel_requested`，就把 13 个叶子全部路由到**一个总恢复 switch**（§4.6），不再发起任何新的 hook/provider/tool。

【设计取舍】为什么是"扁平 13 叶子"而不是嵌套状态树？因为 0.87.0 的一次重构（`runtime-simplification.md`）专门把它做扁了：runtime 从 5,358 行减到 4,654 行（删 704 行，13.1%），并删掉了旧的所有权机制（`installerSignal`/`DriveAbandoned`/`LostOwnership`）。理由之一是**恢复要能直接从 `state.at` 这个扁平叶子分派**，嵌套会让"从哪继续"变得含糊。

## 8.5 三提交协议：intent → effect → settlement

这是可恢复性的核心。以 assistant 生成为例（§0.4 的规范写入顺序）：

```text
TX[ ... operationState = assistant.ready (config snapshot) ]
TX[ upsert state = assistant.effect_pending, 预留 response id R、usage id U ]  ← intent
      … provider 流式输出 …（不确定窗口，进程可能死在这里）
TX[ append pi.pending.assistant_frame/O:R += frame ]   ← 每个非终态事件一帧，非阻塞入队
TX[ insert entry R, insert usage U, upsert branch.tip,
    delete list pi.pending.assistant_frame/O:R,
    upsert state = tools (预留 result id) ]              ← settlement
```

工具调用同理：`call N effect_pending`（记录精确参数与 `replay` 策略）→ 执行 → 提交 `outcome_ready` → 按源序 materialize 成 entry。

【设计取舍】关键点：**在 intent 之后、settlement 之前崩溃，意图和实际效果都无法区分**。Pi 不试图消除这个窗口，而是承认它，并在恢复时按策略处理（见下节）。hooks 走"replay 契约"：hook 结果在消费它的那个事务里才变持久，崩溃前可能重跑——所以**带副作用的 hook 必须幂等**（用 operation id 做 key）。

## 8.6 恢复矩阵：崩溃点决定复盘动作

【代码事实】§4.5 给出两张表。**通用四个崩溃位置**：

| 崩溃点 | 恢复行为 |
|--------|---------|
| intent 提交前 | 当什么都没发生，正常重跑 |
| intent 后、effect 准入前 | `effect_pending`，与"执行中崩溃"不可区分 |
| effect 执行中/后、settlement 前 | 同上，走"未知结果"策略 |
| settlement 提交后 | 直接继续，**绝不重新结算** |

**孤儿 effect 的恢复矩阵**：

| 孤儿断点 | 恢复动作 |
|---------|---------|
| assistant `effect_pending` | 读回 `pendingAssistantFrames`，`reduceAssistantMessageFrames` 重建部分输出，**合成一个零 usage 的 error 响应**（带"请求被中断、前置内容是最后持久化前缀、外部结果未知"警告），删帧列表；之后走普通重试/失败分类 |
| structural（压缩/摘要）`effect_pending` | 整个尝试视为不确定，推进到下一个 `ready` attempt 或按上限失败；已提交的 usage 保留在账本 |
| tool `effect_pending` | 双方声明都 `safe` → 用持久化参数**重执行**；否则**合成中断结果**（保留检查点内容 + 警告），绝不重放不安全的工具 |
| deferred poll `effect_pending` | 无 poll permit → 保持挂起；有 permit 且模型可解析 → 换新 id 重试一次；模型不可用 → 转配置性失败 |

【给新项目】这张表就是"可恢复 Agent"最值钱的部分。它告诉你：**副作用要分级**（`safe` 可重放 / `never` 不可重放），并在 intent 里记下来。没有这个声明，恢复时只能二选一：冒着重复副作用的风险重跑，或丢掉结果。

## 8.7 效果门（Gate）：准入必须同步

【代码事实】`Drive` 拥有一个 split gate（§4.2）：`Gate.admit(invoke)` **同步**检查状态并立即执行；`GateControl` 只在 `Drive` 内部，过程代码只能拿到只读的 `gate`。三种状态：`open` / `aborting` / `closed`。

规范里反复强调的红线：

```ts
await prepareRequest();              // 所有准备在准入前
const admittedContext = withAbortSignal(drive.gate.signal, drive.context);
const stream = drive.gate.admit(() =>   // 检查与调用之间没有 await
  models.streamSimple(model, aiContext, { ...options, signal: admittedContext.abortSignal }),
);
```

【设计取舍】为什么必须同步？因为如果准入检查后还有 `await`，**abort 可能在准备期间抢先**：要么取消生效太晚（已发起请求），要么请求在取消后仍被发出。把"检查 + 调用"压成一个同步表达式，是让"取消一定不会晚于已准入效果"成立的最小条件。

准入清单（§4.2）覆盖：hook 聚合（一个 `admit` 包住整条 pipeline，而非每个 handler）、`Models.streamSimple`/`streamDeferred`/结构摘要请求、真实的 `tool.execute`、以及每个重试定时器的创建。**其余一律不在 gate 内**：commit、公共队列/配置修改、纯分类、事务构造、合成结算、参数/上下文准备、取消对账、被动 listener。

## 8.8 abort / close / fault 三件不同的事

【代码事实】

- **abort（`requestAbort`）**：持久化取消。顺序是：有 live Drive 时同步 `beginAbort()` 阻止新准入 → mutation line 上写 `cancel_requested` → 同一提交里清空 inbox 的 steer/followUp → 提交后 signal gate → 绑定并投递 `operation_abort` 事件。**取消进行时也绝不发起新的 hook/provider/tool**。
- **close**：受控崩溃。不写取消、不写终态，只封住准入、排空已准入的 mutation、关闭存储。重新打开时看到的断点与进程被杀完全一致。
- **fault（`HarnessFault`）**：已准入的存储提交失败 → **整个 harness 故障**，所有调用拒绝，必须重启进程；从最后一次成功事务恢复。这是"绝不接受部分事务"的直接后果。

【重要的区分】调用方 `Context` 的取消只停止**该调用方的观察**，绝不改操作状态；持久化取消只能通过 `requestAbort`。"abort 一个 context"与"持久化取消一个操作"是两码事。

## 8.9 踩坑与设计取舍

【文档事实，来自 §0.6 与 §1.7】

1. **Provider 流不可续传**：harness 从不重新挂接到 Provider 流。已提交的帧只用于"重建最新持久化部分 + 重连显示"，不证明请求如何结束。settled 响应必须**完整落盘后**才被分类。
2. **JSONL 的死字节**（J1，已规范未实现）：JSONL 每次 `set` 都追加，一个 30 轮的 run 会留下约 10 条废弃的 `pi.op.state` 行；逻辑删除立即生效，但物理字节在快照压缩落地前**永不回收**。因此工具作者要自己控制检查点频率（bash：live update 100ms、checkpoint 最多 2s、只在变化时写；50KiB/次，持续变化时约 **15MiB/10 分钟**）。
3. **预写顺序反模式**：SQLite 的每个可能写的事务**必须 `BEGIN IMMEDIATE`**。因为每个 commit 都要先读 `next_seq` 再写，deferred `BEGIN` 会先拿读快照再升级写锁，冲突时 `busy_timeout` 救不了——只能回滚整体重试。
4. **单写者**：一个 Session 同时只允许一个 host 指定的可写 owner；storage 后端不强制这条规则（它是 host 生命周期规则）。

## 8.10 给新项目的落地清单

1. **先定义"副作用分级"**：每个工具声明 `replay: safe | never`，写进 intent。
2. **三存储 + 一个不变量**：会话内容写一次；可变状态只存"当前完整值"；成本单独成账本。
3. **三提交协议**：intent 预留 id → 执行 effect → settlement 一次提交输出 + 用量 + 下一状态。崩溃窗口显式化。
4. **断点是一个扁平的、可整体替换的判别联合**，恢复时直接 `switch`。
5. **准入边界必须同步**：准备与准入分离，检查与调用之间不能有 `await`。
6. **区分 abort / close / fault**：取消是持久化请求，close 是受控崩溃，存储提交失败必须整体故障而非局部降级。
7. **给每个 effect 设计"孤儿恢复"动作**，并在测试里覆盖四个崩溃点（可在每次 `commit` 前后注入异常）。
