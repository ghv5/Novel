# 09 扩展系统：Prompt Templates、Skills 与热插拔 Extensions

> 01–08 讲的是内核。这一篇讲**外壳**：Pi 如何在不改内核的前提下，让用户/第三方往 Agent 里加东西。
> 主要文档：`packages/coding-agent/docs/extensions.md`、`skills.md`、`prompt-templates.md`、`packages.md`。
> 基于 0.87.0。

## 9.1 三种扩展形态

Pi 把"扩展"拆成三种**成本完全不同**的形态，按"从轻到重"递进：

| 形态 | 载体 | 能力 | 需要写代码 | 加载时机 |
|------|------|------|-----------|---------|
| Prompt Template | 一个 `.md` | 一段可复用的提示词 + 参数 | 否 | 每次 `/name` 时展开 |
| Skill | 一个 `SKILL.md` + 脚本/资料 | 一套按需加载的工作流 | 可选 | 常驻"描述"，命中任务时加载正文 |
| Extension | 一个 `.ts` 模块 | 注册工具/命令/UI、拦截事件 | 是 | 启动时加载，可 `/reload` 热更新 |

【设计取舍】这个分级很值得借鉴：**不要把所有扩展都做成"插件代码"**。大多数需求只是"一段提示词"或"一套说明 + 脚本"，用 Markdown 就够了；只有真正需要挂钩子、注册工具时才升级到 TypeScript。

## 9.2 Prompt Templates：最短的扩展

【代码事实】把 `.md` 放进 `~/.pi/agent/prompts/` 或 `.pi/prompts/`，文件名就是命令名（`review.md` → `/review`）。

支持的位置（`prompt-templates.md`）：global、项目（需信任）、package 的 `prompts/` 或 `package.json` 的 `pi.prompts`、settings 的 `prompts` 数组、CLI `--prompt-template`。用 `--no-prompt-templates` 关闭。

参数替换规则：

```
$1, $2, ...            位置参数
$@ / $ARGUMENTS        全部参数拼接
${1:-default}          有值时用值，否则用默认
${@:N} / ${@:N:L}      从第 N 个起 / 取 L 个
```

`argument-hint` 用于自动补全里的占位提示，`<PR-URL>` 表示必填、`[instructions]` 表示可选。

【给新项目】如果只能加一种扩展机制，就加这个。成本极低、收益立刻可见，而且不和内核耦合。

## 9.3 Skills：渐进式披露

【代码事实】Skill 是一个含 `SKILL.md` 的目录（其余文件随意）。Pi 实现 [Agent Skills 标准](https://agentskills.io/specification)，但**故意放宽了一条**：不要求 `name` 等于父目录名（原作者认为该要求对多工具共享的 skill 目录不合理）。

工作方式（`skills.md §How Skills Work`）：

1. 启动时扫描位置，**只抽取 name + description**；
2. 系统提示里以 XML 形式放入"可用 skills"清单；
3. 任务命中时，模型用 `read`（或不可用时的 `bash`）加载完整 `SKILL.md`；
4. 模型按说明执行，用相对路径引用脚本/资料。

> 这就是**渐进式披露（progressive disclosure）**：常驻上下文里只有描述，正文按需加载。

加载位置：global（`~/.pi/agent/skills/`、`~/.agents/skills/`）、项目（需信任）、package、settings、CLI `--skill`。可以用 settings 复用别的 harness 的 skill 目录：

```json
{ "skills": ["~/.claude/skills", "~/.codex/skills"] }
```

Frontmatter 必填 `name` + `description`；可选 `license`/`compatibility`/`metadata`/`allowed-tools`/`disable-model-invocation`。校验大多只告警仍加载，但**缺 description 不加载**；同名冲突保留先发现的。

【设计取舍】Skills 的核心不是"能放脚本"，而是**上下文经济学**：把所有能力都塞进 system prompt 会撑爆窗口、稀释注意力。Pi 的 `description` 质量直接决定"模型会不会正确加载"——文档专门给出"Good vs Poor description"的对比。

【坑】模型不一定主动加载 skill。文档直言："models don't always do this"；对策是提示词，或用 `/skill:name` 强制加载。

## 9.4 Extensions：真正的代码级扩展

【代码事实】Extension 是一个导出 default function 的 TypeScript 模块，接收 `ExtensionAPI`（`extensions.md §Quick Start`）：

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  pi.on("session_start", async (_event, ctx) => ctx.ui.notify("loaded!", "info"));

  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
      if (!ok) return { block: true, reason: "Blocked by user" };
    }
  });

  pi.registerTool({ name: "greet", /* … */ });
  pi.registerCommand("hello", { description: "Say hello", handler: async (a, ctx) => {/* … */} });
}
```

能力面：自定义工具、事件拦截、`ctx.ui` 交互、自定义 TUI 组件、`/命令`、会话持久化 `pi.appendEntry()`、自定义渲染。

自动发现位置（`~/.pi/agent/extensions/`、`.pi/extensions/`）里的扩展支持 `/reload` 热更新；快速测试用 `pi -e ./path.ts`。

## 9.5 事件总线：扩展能挂哪些点

【代码事实】`extensions.md` 的生命周期图（`### Lifecycle Overview`）给出了完整钩子链。按阶段归类：

- **启动/信任**：`project_trust`、`session_start`、`resources_discover`
- **输入**：`input`（可拦截/改写/直接处理）
- **Agent 生命周期**：`before_agent_start`、`agent_start`、`agent_end`、`agent_before_settle`、`agent_settled`
- **Turn**：`turn_start`、`turn_end`
- **上下文/请求**：`context`、`context_with_system`、`before_provider_headers`、`before_provider_request`、`after_provider_response`、`cache_warming_decision`
- **工具**：`tool_execution_start/update/end`、`tool_call`（可 block）、`tool_result`（可改）
- **会话**：`session_before_switch`、`session_before_fork`、`session_before_compact`/`session_compact`/`session_compact_failed`、`session_before_tree`/`session_tree`、`session_shutdown`、`session_info_changed`
- **模型**：`model_select`、`thinking_level_select`
- **UI**：`ui_prompt_start`、`ui_prompt_end`
- 其他：`user_bash`

【设计取舍】这里的钩子比内核的 `AgentLoopConfig`（06 文的 10 个）**多得多**。原因是分层：`AgentLoopConfig` 是**内核**扩展点，面向"别的主循环实现"；extension 事件是**产品层**扩展点，面向"终端用户/插件"。前者要求语义精确、小而稳定；后者允许面广、可热插拔。

## 9.6 注册 API 与动态工具

【代码事实】关键 API（`extensions.md §ExtensionAPI Methods`）：

- `pi.on(event, handler)`：返回 unsubscribe；handler 按扩展加载顺序、再按注册顺序执行；**正在进行的 dispatch 不受增删影响**。
- `pi.registerTool(def)`：可在启动时或之后（`session_start`、命令处理器里）注册，新工具**立即可被 LLM 调用**，无需 `/reload`。支持 `promptSnippet`（进 `Available tools` 一行）与 `promptGuidelines`（追加到 `Guidelines`）。
- `pi.appendEntry()`：只进 TUI、不发 LLM 的持久内容；`pi.sendMessage()`：进 LLM 上下文的消息。
- `pi.setActiveTools()`：运行时启停工具（含动态加入的）。
- `pi.registerProvider()`/`unregisterProvider`：注册自定义 Provider。
- `pi.exec`、`pi.events`、自定义渲染器等。

【坑，原文明确提醒】`promptGuidelines` 是**平铺**追加到 `Guidelines` 的，**不带工具名前缀**。所以每条 guideline 必须自己点名工具：写"Use `my_tool` when…"，绝不能写"Use this tool when…"，否则模型不知道"this"指谁。

## 9.7 安全边界与信任模型

【文档事实，原文多处加粗 Security】

- Skill 与 extension **都能指示模型执行任意操作**，extension 更是**以你的完整系统权限运行任意代码**。只能安装可信来源。
- 项目级资源（`.pi/skills`、`.pi/prompts`、`.pi/extensions`）**只在项目被信任后加载**（`project_trust` 事件、`ctx.isProjectTrusted()`）。
- 扫描/校验只是"宽松 + 告警"：Pi 对标准违规大多只警告，仍加载。

【设计取舍】Pi 选择了"宽松解析 + 显式信任"的组合，而不是"严格沙箱"。这对一个开发者工具是合理取舍：扩展本质上就是本地代码，强行沙箱会限制能力；用"信任提示 + 位置隔离 + 显式 opt-in"来划定边界。

## 9.8 踩坑汇总

| 坑 | 表现 | 对策 |
|----|------|------|
| 模型不加载 skill | 任务命中但正文没进上下文 | 提高 `description` 质量；用 `/skill:name` 强制 |
| guideline 主语不明 | 写了"this tool"模型不知道指谁 | 每条明确点名工具名 |
| 扩展不在发现目录 | `/reload` 无效 | 放到 `~/.pi/agent/extensions/` 或 `.pi/extensions/` |
| 项目资源不加载 | 未信任项目 | 先信任项目；或走 global 位置 |
| 热重载丢状态 | `/reload` 后内存态消失 | 用 `pi.appendEntry()` 做持久化 |
| 事件 handler 慢 | 阻塞分派 | 快速返回；耗时工作异步化（注意 06 文的 `agent_end ≠ idle`） |

## 9.9 给新项目的建议

1. **先做 Markdown 级扩展**（prompts / skills），再做代码级（extensions）。前者覆盖 80% 需求且零耦合。
2. **渐进式披露**：常驻上下文只放"名称 + 描述"，正文按需 `read`。
3. **事件命名按阶段分组**，并保证"增删 handler 不影响进行中的 dispatch"。
4. **区分"进 LLM 的内容"与"只进 UI 的内容"**（`sendMessage` vs `appendEntry`），否则会给用户界面塞进不该给模型看的东西。
5. **信任边界显式化**：项目级资源必须 opt-in，且把"扩展 = 任意代码"写进文档。
6. **动态注册要能立即生效**，否则用户体验会退化成"改一次跑一次"。
