# 06 · 事件流、钩子体系与扩展点

> Pi 用 10 种 `AgentEvent` 驱动 UI，用 `AgentLoopConfig` 的 10 个钩子向宿主开放精确时机的扩展能力。
> 这是"无状态循环 + 有状态包装器"设计能成立的关键。

源码：`packages/agent/src/types.ts`（事件与钩子契约）、`packages/agent/src/agent.ts`（状态归约）、`packages/agent/src/harness/events.ts`（事件总线）。

## 6.1 十种 AgentEvent（生命周期 4 + 消息 3 + 工具 3）

```typescript
// types.ts L485-501（判别联合类型）
type AgentEvent =
  | { type: "agent_start" }                                        // 整个 run 开始
  | { type: "agent_end"; messages: AgentMessage[] }                // 整个 run 结束，携带全部新消息
  | { type: "turn_start" }                                         // 一个 turn 开始
  | { type: "turn_end"; message; toolResults }                     // 一个 turn 结束
  | { type: "message_start"; message }                             // 消息开始
  | { type: "message_update"; message; assistantMessageEvent }     // 消息更新（仅流式 assistant）
  | { type: "message_end"; message }                               // 消息结束
  | { type: "tool_execution_start"; toolCallId; toolName; args }   // 工具开始执行
  | { type: "tool_execution_update"; toolCallId; toolName; args; partialResult }  // 工具流式进度
  | { type: "tool_execution_end"; toolCallId; toolName; result; isError }        // 工具执行完成
```

### 事件发射时序

```
agent_start
└─ turn_start
   ├─ message_start (assistant)
   ├─ message_update × N (流式 delta)
   ├─ message_end (assistant)
   ├─ tool_execution_start (tool 1)
   ├─ tool_execution_update × N (tool 1)
   ├─ tool_execution_end (tool 1)
   ├─ message_start (toolResult 1)
   ├─ message_end (toolResult 1)
   ├─ tool_execution_start (tool 2)
   │  ...
   └─ turn_end
      │
      ├─ turn_start (下一轮，若还有工具调用)
      │  ...
      └─ turn_end
agent_end
```

**关键点**：
- `message_start/update/end` 用于**流式渲染**（UI 实时显示 assistant 输出）
- `tool_execution_start/update/end` 用于**工具进度**（UI 显示"正在读文件..."）
- `turn_start/end` 用于**回合边界**（UI 可以按 turn 分组渲染）
- `agent_start/end` 用于**整个 run 边界**（UI 显示"agent 工作中/完成"）

## 6.2 十个钩子（AgentLoopConfig）

`AgentLoopConfig`（types.ts L189 起）定义了 10 个钩子（`toolExecution` 是执行模式设置，不是钩子），每个有精确的调用时机和契约：

| 钩子 | 调用时机 | 契约 |
|------|---------|------|
| `convertToLlm` | 每次 LLM 请求前（streamAssistantResponse 内） | **必须不抛错**，返回 LLM Message[] |
| `transformContext` | convertToLlm 之前（可裁剪/压缩上下文） | 可返回新 context |
| `prepareRequest` | 每次 provider 请求前（最后一道调整） | 可改 context/model/thinkingLevel |
| `prepareNextTurn` | 每轮 turn 结束后、下一轮开始前 | 可改 context/model/thinkingLevel + 追加消息 |
| `getSteeringMessages` | 内层 while 底部（turn 结束点） | 必须返回 [] 不抛错 |
| `getFollowUpMessages` | 外层 while 底部（agent 将停点） | 必须返回 [] 不抛错 |
| `beforeToolCall` | 工具执行前（prepareToolCall 内） | 可 block/terminate |
| `afterToolCall` | 工具执行后（finalizeExecutedToolCall 内） | 可字段级覆盖 result |
| `finishTurn` | turn 结束、turn_end 发射前 | 返回 `{action:"end"}` 或 `{action:"continue"}` |
| `getApiKey` | 每次 LLM 请求时（解析 provider key） | 返回 string 或 undefined |

### 钩子调用时序图

```
runLoop 内层 while 每轮：
  │
  ├─ [1] prepareNextTurn (上轮完成后)
  │     → 可换 context/model（如触发压缩）
  │
  ├─ [2] 合并 pending 消息
  │
  ├─ [3] prepareRequest (请求前最后调整)
  │
  ├─ [4] streamAssistantResponse 内:
  │     ├─ [4a] transformContext (上下文裁剪/压缩)
  │     ├─ [4b] getApiKey (解析 provider key)
  │     ├─ [4c] convertToLlm (AgentMessage → LLM Message)
  │     └─ [4d] streamFn (实际 LLM 请求)
  │
  ├─ [5] 工具执行:
  │     ├─ beforeToolCall (每个工具前)
  │     ├─ tool.execute
  │     └─ afterToolCall (每个工具后)
  │
  ├─ [6] finishTurn (turn 收尾)
  │
  └─ [7] getSteeringMessages (turn 结束点 drain)

外层 while 底部:
  └─ [8] getFollowUpMessages (agent 将停点 drain)
```

## 6.3 状态归约（processEvents）

`Agent.processEvents`（agent.ts L498-547）是**纯状态机**，把事件流归约成 `AgentState`：

```typescript
switch (event.type) {
  case "message_start" / "message_update":
    state.streamingMessage = event.message;
    break;
  case "message_end":
    state.messages.push(event.message);
    state.streamingMessage = undefined;
    break;
  case "tool_execution_start":
    state.pendingToolCalls.add(event.toolCall.id);
    break;
  case "tool_execution_end":
    state.pendingToolCalls.delete(event.toolCall.id);
    break;
  case "turn_end":
    state.errorMessage = event.message.stopReason === "error" 
      ? event.message.errorMessage : undefined;
    break;
}
// 每个事件归约后，按订阅顺序 await 所有 listener
```

**关键**：
- `streamingMessage` 只保留**当前正在流式**的消息（用于 UI 实时渲染）
- `messages` 是**已完成**的消息列表（用于持久化/回放）
- `pendingToolCalls` 是**正在执行**的工具集合（用于 UI 显示"执行中"）
- 每个事件归约后**顺序 await 所有 listener**（listener 可阻塞，但不影响核心循环正确性）

## 6.4 事件总线（HarnessEventBus）

`harness/events.ts` 提供 `HarnessEventBus`，用于 harness 层的事件分发：

- `on/emit/emitBatch/watch` 接口
- `deliveryTail` 串行化分发（保证事件顺序）
- `structuredClone` 隔离 payload（避免 listener 修改原始事件）
- handler 异常转成 `handler_error` 事件（不中断分发）
- `BufferedEventWatcher` 支持快照 + resnapshot 边界（断线重连）

**与 AgentEvent 的关系**：`AgentEvent` 是 agent-loop 发出的**底层事件**，`HarnessEventBus` 是 harness 层的**事件分发总线**，把 AgentEvent 隔离式地分发给多个订阅者（UI、telemetry、持久化等）。

## 6.5 扩展点总结

Pi 的扩展能力来自**两个层次**：

### 低层：AgentLoopConfig 钩子（10 个）

宿主（coding-agent CLI、SDK 用户）通过 `AgentLoopConfig` 注入钩子，控制 agent 行为：
- 上下文压缩（`transformContext` / `prepareNextTurn`）
- 工具拦截（`beforeToolCall` / `afterToolCall`）
- 轮次控制（`finishTurn`）
- 消息注入（`getSteeringMessages` / `getFollowUpMessages`）
- API key 管理（`getApiKey`）

### 高层：AgentHarness（harness 层）

`AgentHarness`（`harness/agent-harness.ts`）在 Agent 之上再包一层，提供更高级的操作接口：
- `OperationRequest`（prompt/skill/prompt_template/compaction/navigation 五种操作）
- `DriveOutcome`（settled/waiting-retry/waiting-deferred）
- `WatchHandle`（事件订阅句柄）

**设计意图**：低层钩子细粒度控制循环行为，高层 Harness 提供语义化的操作接口。两层解耦，宿主可选择使用哪一层。

## 6.6 核心设计总结

| 设计决策 | 原因 |
|---------|------|
| 10 种 AgentEvent（判别联合） | 类型安全，UI 可精确 switch 处理 |
| 10 个钩子精确时机 | 每个钩子有明确契约，宿主可预测行为 |
| 纯状态归约（processEvents） | 状态机与事件解耦，listener 不污染核心状态 |
| 事件总线（structuredClone 隔离） | 多订阅者互不干扰，handler 异常不中断分发 |
| 两层扩展（钩子 + Harness） | 细粒度 + 语义化，宿主按需选择 |

## 6.7 如何验证

这些行为都可以在不启动真实模型的情况下验收：

- **事件计数完整性**：对一个 faux provider 跑一次带工具的 turn，收集的事件序列应严格符合 6.1 的时序（`agent_start → turn_start → message_start/update*/end → tool_execution_* → message_start/end(toolResult) → turn_end → agent_end`）。
- **`agent_end ≠ idle`**：注册一个故意阻塞的 listener，断言 `agent_end` 已发出但 `state.isStreaming` 仍为 `true`；listener settle 之后才变 `false`。
- **listener 异常隔离**：让一个 listener 抛错，断言其余 listener 仍被调用，且核心循环状态不受污染（事件总线应转成 `handler_error`）。
- **钩子时机**：分别在 `beforeToolCall` 返回 `block`、`afterToolCall` 覆盖字段、`finishTurn` 返回 `{action:"end"}` 时，断言工具没有被执行、结果被覆盖、循环在 `turn_end` 后停止且不再 poll 队列。
- **error/aborted 硬退出**：构造 `stopReason==="error"` 的响应，断言 `finishTurn` 仍被调用但其 `{action:"continue"}` 被忽略，事件序列以 `agent_end` 结束。
